The mobile client uses a JSON REST API plus Server-Sent Events. The application
API is versioned under `/api/v1`; Better Auth owns `/api/auth/*`; a few public
HTML and platform-association routes live at the origin root.

This page is an **implementation inventory**, not a promise of long-term API
stability. Musubi is pre-1.0 and does not currently generate an OpenAPI schema.
The route registry in `apps/api/src/index.ts` (with task routes in
`apps/api/src/task_routes.ts`), shared Zod schemas in `packages/types`, and
handlers in `apps/api/src/handlers/` are authoritative.

## Authentication

Most application routes require:

```http
Authorization: Bearer <session-token>
```

`requireAuth` resolves the token in two stages:

1. Better Auth session (`auth.api.getSession`);
2. SHA-256 lookup of a non-expired credential in `member_tokens` for a
   federated shadow member.

The second path authenticates identity only. Resource handlers must still
authorize calendar, event, or task access through `calendar_members` and the
shared permission matrix. A valid bearer token alone grants no calendar access.

Better Auth also supports its normal cookie-based flows under `/api/auth/*`.
Use the generated `authClient` in the app instead of reimplementing sign-in,
sign-up, session, social-linking, password-reset, or deletion calls.

## Conventions

### JSON and dates

Application JSON uses the schemas from `@musubi/types`. Date fields cross HTTP
as ISO 8601 strings and are coerced back to `Date` by Zod or client/cache
boundaries.

The global JSON body limit is **512 KB**. Calendar import is the exception: it
uses `text/calendar` with a route-local **10 MB** limit.

### Success and errors

Creates normally return `201`; reads/updates/deletes return `200`; several
side-effect-only routes return an empty `200`.

Typed application errors map to:

| Error kind | HTTP |
| --- | ---: |
| `BadRequest` | 400 |
| `Unauthorized` | 401 |
| `Forbidden` | 403 |
| `NotFound` | 404 |
| Unknown/unhandled | 500 |

Uncaught Zod validation failures are also normalized to `400`. Event endpoints
validate canonical UUID shape before issuing PostgreSQL queries, and
`GET /events?since=` rejects non-string or invalid timestamps. Malformed client
input must not surface as a database-flavoured `500`.

The central error middleware includes the request correlation id:

```json
{
  "error": "You don't have permission to editEvents on this calendar.",
  "requestId": "..."
}
```

The same value is returned in `x-request-id` and attached to structured logs.
Endpoint-specific conflicts can return their own typed JSON; use the response
header for correlation even when the body has no `requestId`.

## Server and realtime

| Method and path | Auth | Response |
| --- | ---: | --- |
| `GET /api/v1/server` | Public | `{ version, minClientVersion, socials, socialsWeb, syncProviders, googleAvailability, email, emailVerificationRequired, pushPublicKey }` |
| `GET /api/v1/server/ok` | Public | `{ ok: true, version }` |
| `GET /api/stream` | Required | Long-lived `text/event-stream` |

SSE frames contain one JSON object:

```text
data: {"type":"event_updated","payload":{...}}
```

Current event types:

| Type | Client reaction |
| --- | --- |
| `event_created` | `localAddEvent` |
| `event_updated` | `localUpdateEvent` |
| `event_removed` | `localRemoveEvent` |
| `task_created` | Refresh tasks; resolve currently authorized task content |
| `task_updated` | Refresh tasks; do not merge a private task snapshot from the frame |
| `task_removed` | Refresh tasks and remove inaccessible/deleted items |
| `calendar_updated` | Merge into calendar store |
| `calendar_removed` | Drop calendar and its orphaned event links |
| `attendance_changed` | Refresh open attendee state |
| `external_sync` | Silent delta refresh; do not trigger provider sync again |
| `settings_updated` | Refetch settings; carries only `{ revision }` |
| `reminders_updated` | Refetch reminder rules and reschedule; carries no payload |
| `page_created` | Add the `PageDocument` in `data.page` |
| `page_updated` | Replace the `PageDocument`; dedupe by `revision` |
| `page_removed` | Drop the page id in `data.id`; the default may have moved |
| `federated_sync` | Something changed on the connected server in `data.server`; refetch that server's data |

Page, settings, and reminder events fan out only to the acting user's own sessions,
including the originating one, which discards the duplicate by revision.

Task mutation frames contain only `payload: { id, revision, actorID }`, with the
actual mutation actor. They reach current and previous affected calendar
members and the actor, so unlink/deletion can invalidate old views without
exposing text or private membership lists. Provider pulls use `external_sync`
rather than inventing a human actor. Activity notices are session-only.

SSE is best-effort and has no replay buffer. Recovery uses event delta sync and
a full authenticated task read; provider delivery evidence is durable and
separate from activity notices.

```ts
type Event = {
  id: string;
  creatorID: string;
  organizer: string;
  title: string;
  color: string;
  start: Date;
  end: Date;
  calendars: string[];
```

Identity and authority are server-owned: create overwrites `creatorID`; update

## Tasks

For the user-facing flow, see [Shared tasks](/docs/guides/shared-tasks/).
All routes below require authentication. The task contract is defined in
`packages/types/src/task.ts`; authorization and commits are implemented in
`apps/api/src/handlers/tasks.ts` and `packages/db/src/queries/tasks.ts`.

### Reads and authority

| Method and path | Response |
| --- | --- |
| `GET /api/v1/tasks` | `{ tasks: Task[] }`, the full active authorized set, deduplicated by task ID |
| `GET /api/v1/tasks/:taskId` | One currently readable `Task`, or `404` |

`Task` has `id`, `creatorID`, `calendarID`, `title`, `description`, `status`,
`start`, `due`, `isAllDay`, `completedAt`, `percentComplete`, `priority`,
`recurrence`, `relatedTo`, `sequence`, and `url`. Date values are ISO strings
on the wire. Status is `needs-action`, `in-process`, `completed`, or `cancelled`;
progress is an integer from 0 to 100 and priority an integer from 0 to 9.

The v0.2.2 response adds `originCalendarID`, readable `calendarIDs`, a positive
`revision`, optional `providerReadRetiredGeneration`, and
`capabilities: { edit, delete, link, fork, unlinkCalendarIDs }`.
`calendarID` is a compatibility home alias, never proof of editing rights on a
secondary calendar. An unreadable home name and unreadable memberships are
not disclosed. Read schemas accept older DTOs without the added fields; a
missing revision requires refresh before mutations.

Only home `editTasks` authorizes content changes, completion, or global delete.
A current readable source plus destination `editTasks` can authorize a link or
copy; destination `editTasks` can authorize removing a secondary membership.
Source-access retirement and rehydration checks still apply.

### Mutations

All writes use **`/api/v1/task-mutations`**. Task and calendar route/body IDs,
and a supplied `Idempotency-Key`, must be UUIDs.

| Method and path | Body | Success |
| --- | --- | --- |
| `POST /api/v1/task-mutations` | `TaskCreate`: `id`, home `calendarID`, `title`, and optional content fields | `201`, mutation receipt |
| `PATCH /api/v1/task-mutations/:taskId` | `{ patch, expectedRevision, expectedProviderReadRetiredGeneration? }` | `200`, mutation receipt |
| `PUT /api/v1/task-mutations/:taskId` | `TaskReplaceRequest`: full draft with home `calendarID`, `expectedRevision`, and optional privacy generation | `200`, mutation receipt; cannot move home or replace memberships |
| `POST /api/v1/task-mutations/:taskId/link` | `{ calendarID, expectedRevision, expectedProviderReadRetiredGeneration? }` | `200`, same logical task with another membership |
| `POST /api/v1/task-mutations/:taskId/fork` | Same body as link | `201`, new independent task with its destination as home and revision 1 |
| `DELETE /api/v1/task-mutations/:taskId` | `{ expectedRevision, unlinkCalendarID?, expectedProviderReadRetiredGeneration? }` | `200`, deletion receipt; secondary unlink when supplied, global delete otherwise |

Create content fields use the Task content names above, excluding
server-owned creator, memberships, revision, privacy generation, capabilities,
and provider `sequence`. Creation defaults to `needs-action`, progress/priority
0, and `isAllDay: false`. A PATCH is strict and accepts only editable content
fields; omitted fields keep their values instead of acquiring create defaults.
Completing sets progress to 100 and supplies a completion time when absent;
reopening clears completion time and normally resets completed progress to 0.

Send the current positive `expectedRevision` for every existing-task mutation.
After provider source retirement, also send the current
`expectedProviderReadRetiredGeneration`. Admission rechecks source scope,
permissions, and these fences under database locks. A stale fence returns
`409`, `code: "task-source-changed"`, `localCommitted: false`.

A committed mutation returns:

```ts
type TaskMutationReceipt = {
  task: Task | null;        // a current authorized read, with positive revision
  localCommitted: true;
  delivery?: TaskDelivery;
};
```

Deletion also returns `{ id, revision, removed }`; `removed` is false for a
secondary unlink. `task` can be null after a successful commit if access was
lost or reconciliation could not read the task. This still acknowledges the
saved mutation: close the saved draft and refresh. `localCommitted: true` does
not claim successful delivery to every provider.

`Idempotency-Key` is a mutation UUID scoped to the actor. Creation uses the task
UUID by default; other operations generate a fresh key if omitted. The durable
ledger also covers native-only mutations. Ordinary duplicate mutations return
`409`, `code: "task-mutation-duplicate"`, `localCommitted: false`; the key is not
a generic replay guarantee.

An **exact fork retry** is the exception: keeping the original key, destination,
source revision, and privacy generation recovers the same committed copy with
`201`, even after a lost response or a later source change. Reconciliation reads
the copy using current permissions and may return `task: null`; it neither
recreates the copy nor emits another creation notification. Reusing the key for
a different request returns `409`. `409` with
`code: "task-fork-not-committed"`, `localCommitted: false` is terminal proof
that this intent did not commit. Only that proof releases the pending intent
for a deliberate new copy of a refreshed source; a transport error or generic
conflict does not. Client intent identifiers are held in session memory,
isolated by server/actor, rather than persisted across app/browser restarts.

### Delivery receipts and retry

| Method and path | Request | Response |
| --- | --- | --- |
| `GET /api/v1/task-deliveries?cursor=<UUID>` | Optional UUID keyset cursor; no other query keys | `{ items: [{ taskId, savedTitle }], nextCursor }`; up to 25 owned unresolved/cancelled subjects per page, including retained deletes |
| `GET /api/v1/tasks/:taskId/delivery` | — | `TaskDelivery`: `{ taskId, localRevision, targets }` |
| `POST /api/v1/tasks/:taskId/delivery/:operationId/retry` | No body or `{}`; cannot edit the saved operation | `202`, refreshed `TaskDelivery`; 30 requests/minute per user |

Each target has `operationId`, `calendarId`, nullable `calendarName`, `provider`,
`action` (`create`, `update`, or `delete`), `status`, `revision`, `owned`, nullable
`issue`, and `updatedAt`. Status is one of `pending`, `attempting`, `completed`,
`not-needed`, `conflict`, `not-written`, `unconfirmed`, `retry`, `blocked`, or
`cancelled`. When an older operation blocks a destination, the receipt shows
that blocker rather than hiding it behind the latest operation.

Shared readers see only currently readable targets; connection owners may
inspect their retained evidence. Titles come from current authorized reads,
with `Task` as the fallback. Payloads, remote addresses, ETags, and raw provider
errors never enter these DTOs. Delivery responses are `private, no-store`.

Retry requires operation ownership, current destination editing rights and
source scope, no uncertainty/remote conflict snapshot, an admissible
`not-written`, `blocked`, or `retry` state, and a completed/not-needed
predecessor. Conflicts, unsupported writes, and uncertain CREATE cannot be
retried. A refused retry returns `409`,
`code: "task-delivery-retry-unavailable"`; a missing/unowned operation is `404`.
The `202` acknowledges re-admission, not remote success.

### Client/API compatibility

| Client route | API | Result |
| --- | --- | --- |
| Legacy writes under `/api/v1/tasks` | v0.2.2 API | `426`, `code: "task-client-upgrade-required"`, `localCommitted: false`, before preflight or DB writes |
| New `/api/v1/task-mutations` | Older API without that namespace | `404`; retain draft and update server, with no fallback to legacy writes |
| New `/api/v1/task-mutations` | v0.2.2 API | Revision/privacy-fenced writes and explicit committed receipts |

## Notification emails

Sent because a **person** did something, as opposed to a reminder, which is a
promise you made to yourself. The `settings.notificationEmails.eventChanged`
switch is on by default.

| What | When | Batched |
| --- | --- | --- |
| An event moved or was cancelled | Only the start/end changing or `isCanceled` going true. Guests who have not declined, minus whoever made the change | Yes — `pending_notifications`, one email per person per batch |
| A calendar invitation | Somebody typed an address and pressed send | No — transactional, and it has no preference for the same reason a password reset does not |

Batched notifications wait `BATCH_DELAY_MS` (3 minutes) from the **first**
change, never extended: rearranging an afternoon is one email, and somebody who
keeps fiddling still tells people something. Rows are only deleted once the mail
is accepted, so a failed send is retried — and abandoned after 24 hours, because
nobody needs to hear on Tuesday that Monday moved.

## Pages

A Page is a private per-user calendar view profile: name, chosen view, visible
calendars, and simple filters. Pages are never shared with calendar members —
two members of the same calendar keep independent Pages.

| Method and path | Request / response |
| --- | --- |
| `GET /api/v1/pages` | Active Pages ordered by position; lazily creates or repairs the default Page |
| `POST /api/v1/pages` | `{ name, config }`; server assigns id, position, and `revision` |
| `PUT /api/v1/pages/reorder` | `{ pageIds, defaultPageId? }`; atomically renumbers positions and moves the default |
| `GET /api/v1/pages/:id` | One owned Page; `404` otherwise |
| `PATCH /api/v1/pages/:id` | `{ baseRevision, name, config }`; explicit save |
| `DELETE /api/v1/pages/:id` | Soft delete; the default deterministically moves to the next survivor |

`PageDocument`, `PageConfigV1`, and the request schemas are defined in
`packages/types/src/pages.ts`. The config is versioned JSONB (`schemaVersion`
plus a discriminated `view` union and `calendarVisibility`) saved atomically
with one `revision`. Saves are compare-and-swap: a stale `baseRevision` returns
`409` with `{ error: "PAGE_CONFLICT", current }` and never a silent overwrite.
Calendar ids inside the config are not foreign keys — reads ignore calendars the
user can no longer access. A partial unique index enforces at most one active
default Page per user.

`PUT /api/v1/pages/reorder` is a full replacement write: `pageIds` must contain
every active owned Page exactly once. Omitting `defaultPageId` preserves the
current default; including it moves the flag atomically with the order. Position
and default changes increment the affected Page revisions so realtime clients
can apply them.

## Federation

| Method and path | Auth | Body / response |
| --- | ---: | --- |
| `POST /api/v1/federation/accept` | Invite token; optional current member bearer proves an existing shadow | `{ token, profile: { name, email, homeServer, image? } }` → `{ memberToken, memberTokenExpiresAt, userID, calendar }` |
| `POST /api/v1/federation/token/rotate` | Member token | Compare-and-swap exchange → `{ memberToken, memberTokenExpiresAt }` |
| `DELETE /api/v1/users/connections/musubi` | Session | `{ server }` — drop a federated connection |
| `GET /api/v1/federation/connections` | Session | The caller's federated connections **without** the credential: `[{ id, label, remoteUserID, server }]` |
| `GET /api/v1/federation/preview?server=&token=` | Session | Fetches another server's public invite preview on the caller's behalf; rate-limited |
| `POST /api/v1/federation/connect` | Session | `{ server, token }` — runs the accept handshake server-side and stores the connection; returns `{ server, calendar }` and **never a token** |
| `ANY /api/v1/federation/s/:connectionId/api/v1/*` | Session | Gateway: forwards to the connected server with the member token attached |

The gateway (ADR-005) exists so a client never holds a cross-server credential.
`:connectionId` is a `musubi_accounts` row id owned by the caller, so the target
origin is read from the database and cannot be influenced by the request; only
`/api/v1/*` paths are forwarded, the home session cookie is dropped, upstream
status codes are relayed unchanged, and an unreachable origin returns `502`
`FederatedServerUnreachable`. Private, loopback and link-local targets are
refused unless `FEDERATION_ALLOW_PRIVATE_HOSTS=true` (LAN self-hosting). The
preview and connect routes take the origin from the request rather than the
database, so the SSRF guard is the only boundary there — hence the tighter rate
limits.

The member token has no route out of the server: reading connections with their
decrypted token, and storing a client-supplied one, were both removed once the
clients moved onto the gateway. `POST /api/v1/federation/connect` is the only way
a connection is created, so a credential can only ever be one this server
obtained itself.

The returned member token is shown once; the origin stores only its SHA-256
hash. It expires after 90 days and the client rotates it in the final 14 days.
Removing the shadow's last calendar membership revokes its token rows
transactionally. The home server stores a roaming copy encrypted with
`CALDAV_ENC_KEY`.

Profile claims on a first accept are display-only and always create an isolated
shadow. The origin reuses an existing shadow only when the request presents its
current bearer token; submitted email/home-server text alone cannot inherit
prior memberships.
Read the [federation trust model](/docs/architecture/federation/#trust--security-model)
before changing these routes.

## Adding or changing an endpoint

Update all of these seams in one change:

1. shared Zod schema/type when the payload is reusable;
2. query function in `packages/db/src/queries/`;
3. handler validation, authorization, persistence, provider behavior, SSE;
4. route registration and static-before-parameter ordering;
5. client method in `apps/client/services/api.ts`;
6. tests for happy, unauthenticated, forbidden, invalid, and retry/idempotency paths;
7. this inventory and the relevant architecture page.

The full recipe is in [API Server → How to add an endpoint](/docs/architecture/api/#how-to-add-an-endpoint).
