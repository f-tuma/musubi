Run workspace commands from the repository root unless a section says
otherwise. Prefer `pnpm --filter <workspace> ...` over changing directories:
copy-pasted commands then work from the same location in local shells and CI.

This page is a guide to commonly used commands, not a complete inventory. The
[root `package.json`](https://github.com/f-tuma/musubi/blob/main/package.json)
scripts, each workspace's own scripts, and the
[Quality workflow](https://github.com/f-tuma/musubi/blob/main/.github/workflows/quality.yml)
define what actually runs. The
[documentation ownership map](https://github.com/f-tuma/musubi/blob/main/docs/project/brief.md#vlastnictví-dokumentů)
(Czech) lists which file owns each kind of project fact.

## Daily development

| Goal                                                   | Command                                |
| ------------------------------------------------------ | -------------------------------------- |
| Activate the repository's exact pnpm version           | `corepack enable`                      |
| Install exactly the workspace declared by the lockfile | `pnpm install --frozen-lockfile`       |
| Start API, native Metro, web, docs, and web Storybook in the Turbo TUI | `pnpm dev` |
| Start the same tasks with copyable logs                | `pnpm exec turbo run dev storybook --ui=stream` |
| Start only the API                                     | `pnpm --filter @musubi/api dev`        |
| Start only the web client (port 3000)                  | `pnpm --filter @musubi/web dev`        |
| Start only web Storybook (port 6006)                   | `pnpm storybook:web`                   |
| Start only Expo/Metro                                  | `pnpm --filter @musubi/client start`   |
| Build/install Android development client               | `pnpm --filter @musubi/client android` |
| Build/install iOS development client (macOS)           | `pnpm --filter @musubi/client ios`     |
| Start only Starlight                                   | `pnpm docs:dev`                        |

The API's `dev` script applies pending migrations before it starts. The web
dev server proxies `/api` to the API on `127.0.0.1:7531`. The native client
package's `dev` script uses Metro's `--localhost` mode. Use `start` when a
physical device needs LAN discovery.

## Verification

```sh
pnpm check
```

`check` is the local contributor baseline. It validates release metadata, the
API route/realtime/news contracts and peer dependencies, typechecks the
workspaces, runs the workspace test suites, lints the native and web clients,
then builds the web client and documentation site. The `check` script in the
root `package.json` is the exact definition. Packages whose tests import
`@musubi/config` need the root `.env` from
[Run Musubi locally](/docs/guides/running-locally/), or `DATABASE_URL`,
`ENVIRONMENT` and `BETTER_AUTH_URL` in the environment, as the Quality job sets.

**`check` does not run the browser E2E suite.** A change can pass `check` and
still break E2E. Before opening a pull request that touches the web client, run:

```sh
pnpm verify   # check, then the web E2E suite
```

Neither command is the whole pull-request gate; see
[Continuous integration](#continuous-integration).

### Fast scenarios while editing

Start with the smallest JSON scenario for the behavior you are changing:

```sh
pnpm test:behavior --list
pnpm test:behavior --suite task-inspector --scenario conflict-keeps-draft --json
```

That example runs the production web task inspector, task serializer and HTTP
client in Vitest/jsdom with fixture HTTP responses. It needs no database or
provider, and it proves nothing about real database, authentication or provider
behavior. Choose the suite that matches your change;
[behavior-scenarios.md](https://github.com/f-tuma/musubi/blob/main/docs/testing/behavior-scenarios.md)
describes each suite and the boundary it replaces. After the fast loop passes,
`pnpm test:behavior:browser` replays the task-inspector scenarios in Chromium
against the web dev server (Playwright starts one when none is running), still
with fixture API responses.

Run an individual layer while iterating:

| Check                                  | Command                                                           |
| -------------------------------------- | ----------------------------------------------------------------- |
| All TypeScript                         | `pnpm typecheck`                                                  |
| Client TypeScript                      | `pnpm --filter @musubi/client exec tsc --noEmit`                  |
| API TypeScript                         | `pnpm exec tsc -p apps/api/tsconfig.json --noEmit --skipLibCheck` |
| Web TypeScript                         | `pnpm --filter @musubi/web typecheck`                             |
| Workspace test suites                  | `pnpm test`                                                       |
| API route, realtime, and news contracts | `pnpm check:contracts`                                           |
| Browser E2E (Chromium; starts a dev server if none runs) | `pnpm test:e2e`                                 |
| `check`, then web E2E                  | `pnpm verify`                                                     |
| Storybook interaction + accessibility  | `pnpm storybook:web:test`                                         |
| Docs production build + Pagefind index | `pnpm docs:build`                                                 |
| Web + docs build (Turbo)               | `pnpm build`                                                      |
| Native + web ESLint                    | `pnpm lint`                                                       |
| Web ESLint only (shadcn rules)         | `pnpm --filter @musubi/web lint`                                  |
| Workspace peer dependencies            | `pnpm peers:check`                                                |
| Release/toolchain metadata             | `pnpm release:verify`                                             |
| Secrets in the browser bundle          | `pnpm scan:bundle`                                                |

`pnpm scan:bundle` builds the web client with a canary in every server-only
variable (`BETTER_AUTH_SECRET`, `DATABASE_URL`, `SMTP_PASS`, …) and fails if one
of them turns up in a file the browser can fetch. It also matches private-key
blocks, credentialled database URLs and provider key prefixes, and — on a machine
that has a real `.env` — the actual values in it. CI runs it as its own job.

<Aside type="note" title="Native lint uses a warning budget; web lint allows none">
  `pnpm lint` has zero errors. The web client lint allows no warnings. The
  native client uses the warning budget
  configured in `apps/client/package.json` for known React Compiler/hook
  diagnostics. Most are Reanimated shared-value, gesture live-ref, and legacy
  effect-dependency findings. The three compiler rules that previously made lint
  unusable remain visible as warnings, while the package script prevents the
  baseline from growing. Fixing a warning lowers the budget in
  `apps/client/package.json`; never raise it to land a change.
</Aside>

## Continuous integration

[`.github/workflows/quality.yml`](https://github.com/f-tuma/musubi/blob/main/.github/workflows/quality.yml)
runs for every pull request and every push to `main`. It has 21 jobs. One of
them runs `pnpm check` and verifies that generating Drizzle migrations leaves no
diff. The others cover database integration (four shards against PostgreSQL),
web E2E (four shards), Storybook interaction and accessibility, the browser
bundle secret scan, API, web and docs image builds (including arm64), web and
API container smoke tests, the native Android build, old-client compatibility
contracts and observability (metrics, log redaction, alert and Prometheus
configuration). The job names in the workflow are
the authority.

A green `pnpm check` or `pnpm verify` on your machine does not mean Quality is
green. Pull requests merge only when every required check passes for the head
commit.

### Tests

Tests live next to the code they cover. Packages use Vitest, `node --test` or
plain `tsx` assertion files; follow the convention of the package you are
changing. The root `test` script and each workspace's `test` script list what
runs.

Federation also has an opt-in database lifecycle check:

```sh
ENVIRONMENT=test DATABASE_URL=postgresql://... BETTER_AUTH_URL=http://localhost:7531 \
  pnpm test:federation-db
```

Run it only against a disposable, fully migrated PostgreSQL database. It creates
and removes scoped fixtures, and verifies expiry cleanup, compare-and-swap
rotation, unproved-profile isolation, proved shadow reuse and final-membership
revocation.

`pnpm test:db` runs the database integration set that CI shards across four
jobs. Run it only against a disposable, fully migrated PostgreSQL database.

### Provider database integration

```sh
ENVIRONMENT=test \
DATABASE_URL=postgresql://... \
BETTER_AUTH_URL=http://localhost:7531 \
BETTER_AUTH_SECRET=<test-only-secret> \
pnpm test:provider-db
```

Run this only against a disposable, fully migrated PostgreSQL database. The
test starts its own local fake OAuth token endpoint, scopes fixtures to random
IDs, and cleans them up. It verifies encrypted token rotation,
account-specific permanent revocation and transient retry behavior without
live Google/Microsoft credentials.

## Database

| Goal                                | Command                     |
| ----------------------------------- | --------------------------- |
| Generate SQL from `schema.ts`       | `pnpm db:generate`          |
| Apply pending PostgreSQL migrations | `pnpm db:migrate`           |
| Start only the bundled database     | `docker compose up -d db`   |
| Inspect database service            | `docker compose ps db`      |
| Tail database logs                  | `docker compose logs -f db` |

The account-scoped OAuth fallback has a PostgreSQL integration self-check:

```sh
ENVIRONMENT=test \
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/musubi_test \
BETTER_AUTH_URL=http://localhost:7531 \
pnpm test:db:oauth
```

<Aside type="caution">
  Use a disposable, migrated test database. The script refuses to run unless
  `ENVIRONMENT=test`, creates uniquely named users/accounts, asserts isolation
  across users, providers, and sibling accounts, then removes its fixtures.
</Aside>

Always review generated SQL:

```sh
pnpm db:generate
git diff -- packages/db/drizzle
pnpm db:migrate
```

Schema changes and their migration must ship together. Drizzle cannot infer
intent for every rename; verify that a rename did not become destructive
drop-and-create SQL.

## Documentation

```sh
pnpm docs:dev
pnpm docs:build
```

The dev URL is `http://localhost:4321/docs/`. The build validates Starlight
frontmatter, MDX/component rendering and Mermaid transformation, then creates
the Pagefind search index. Browser QA/link crawling is a separate verification
step; a successful build alone does not prove every handwritten URL resolves.

The docs are served under `/docs`, so test that prefix explicitly. The generated
files live under `packages/docs/dist/` and are ignored.

## Versions and releases

[`docs/releasing.md`](https://github.com/f-tuma/musubi/blob/main/docs/releasing.md)
is the single pointer to the current release and its runbook; the
[Releases](/docs/operations/releases/) page explains the release model. The
commands below are the local version checks.

The root `package.json` is the single source for both the Musubi product version
and pnpm:

- `version` is the user-visible SemVer release. `apps/client/app.config.ts`
  reads it directly for the native Expo version.
- `packageManager` pins the pnpm version Corepack uses locally, in CI, and in
  the Docker builds.
- workspace manifests are private and intentionally have neither field.
- EAS keeps platform build numbers remotely; those monotonically increasing
  numbers are separate from the user-visible product version.

For a release, update the root `version` and its `PRODUCT_VERSION` mirror in
`packages/types/src/version.ts`, then validate both:

```sh
pnpm release:verify
pnpm release:verify 0.1.2
pnpm check
```

The optional argument represents the version requested by the release job and
must match the manifest. The validator also rejects nested toolchain/version
metadata and distribution placeholders. The manual **Publish Docker image**
workflow runs the same command before logging in to Docker Hub, publishing an
image, or creating a tag; release gating and promotion are described in
`docs/releasing.md`.

Production iOS builds require a valid App Store or TestFlight update URL.
The production profile supplies the existing public beta channel through
`EXPO_PUBLIC_IOS_TESTFLIGHT_URL`; the update action opens TestFlight. When iOS is
publicly released, set `EXPO_PUBLIC_IOS_APP_STORE_URL` in the EAS production
environment to a real direct listing with a nonzero numeric ID. The app prefers
that listing. `app.config.ts` and the release validator reject malformed supplied
URLs. API/web release metadata and Android do not require an iOS listing.

## Docker and self-hosting

<Tabs>
  <TabItem label="Plain Docker Compose">

```sh
docker compose up -d              # full stack: gateway + web + api + db
docker compose ps
docker compose logs -f api
docker compose pull && docker compose up -d

docker compose -f docker-compose.api.yml up -d   # API + db only
```

  </TabItem>
  <TabItem label="Dokploy">

```sh
docker compose -f docker-compose.dokploy.yml config
PUBLIC_HOST=musubi.example.com docker compose -f docker-compose.dokploy.yml up -d
```

The Dokploy file expects the external `dokploy-network` and `PUBLIC_HOST`; in
Dokploy itself both come from the project, so this is only for checking the
file by hand.

  </TabItem>
  <TabItem label="Build API locally">

In `docker-compose.yml`, replace the published `image:` with the commented
`build:` block (either service — the web image has one too), then run:

```sh
docker compose up -d --build
```

  </TabItem>
  <TabItem label="Build docs locally">

```sh
docker build -f packages/docs/Dockerfile -t musubi-docs:local .
docker run --rm -p 4321:4321 musubi-docs:local
```

Open `http://localhost:4321/docs/`.

  </TabItem>
</Tabs>

Container startup applies PostgreSQL migrations through
`packages/db/src/migrate.ts` before starting the API.
All runtime images use digest-pinned Node, frozen installs, health checks, and a
non-root user. The API and docs use production `pnpm deploy` closures; the web
builder installs its full build graph, but only Nitro output reaches runtime.
Global npm/Corepack binaries are removed from runtime stages.

## Backups

```sh
./ops/backup-postgres.sh
./ops/verify-postgres-backup.sh /path/to/musubi-backup.dump
```

Common overrides:

```sh
MUSUBI_BACKUP_DIR=/var/backups/musubi \
MUSUBI_BACKUP_RETENTION_DAYS=30 \
./ops/backup-postgres.sh
```

The backup script uses a private umask, writes to a partial file, validates the
dump with `pg_restore --list`, and only then publishes it. The verification
script restores into an isolated temporary PostgreSQL container.

## Before opening a pull request

```sh
git status --short
git diff --check
pnpm test:behavior --suite <suite> --scenario <id> --json   # closest scenario
pnpm check
```

Then run the platform-specific flow you changed. Examples:

- API handler: happy path, unauthorized request, forbidden role, invalid body.
- Native client interaction: iOS and Android where practical, plus cold cache
  and refreshed data.
- Web client interaction: the flow in a browser, light and dark themes, a
  narrow viewport and keyboard use; follow the
  [Musubi UI rules](https://github.com/f-tuma/musubi/blob/main/.agents/skills/musubi-ui/SKILL.md).
- Provider adapter: create/update/delete, all-day, recurrence, cursor reset,
  read-only calendar, token expiry.
- Documentation: desktop + mobile navigation, search, changed links, and a
  production build.

The pull request then needs every required Quality job green for its head
commit.
