The Starlight site in `packages/docs/` is the canonical project documentation.
Files under the repository-root `docs/` hold implementation contracts, web UI
rules, release records, dated audits and compatibility pointers. Reader-facing
pages link to those details where needed; current behavior belongs in the site
as well as in its source contract.

## Information architecture

Put a page where its reader will look first:

| Section | Use it for |
|---|---|
| Start Here | First run, onboarding, and symptom-based recovery |
| Architecture | Mental models, invariants, and cross-layer flows |
| Provider Guides | Provider-specific setup, mapping, limits, and debugging |
| Reference | Exact commands, environment, HTTP surface, vocabulary |
| Operations | Deployment, observability, release, and native-widget runbooks |
| Contributing | Workflow, documentation standards, and audit debt |

A page should begin with its purpose and audience. Prefer one canonical
explanation, then link to it from related pages instead of maintaining several
slightly different copies.

## Local workflow

<Steps>

1. **Run Starlight.**

   ```sh
   pnpm docs:dev
   ```

   Open `http://localhost:4321/docs/`. The `/docs` base path is part of the
   production contract, so root-relative internal links start with `/docs/`.

2. **Edit content.**

   Pages live in `packages/docs/src/content/docs/`. Use lowercase, stable
   filenames and descriptive frontmatter:

   ```md
   ---
   title: Provider name
   description: What a contributor can accomplish after reading this page.
   ---
   ```

3. **Add navigation deliberately.**

   The sidebar is explicit in `packages/docs/astro.config.mjs`. New pages are not
   discoverable until their `slug` is placed in the appropriate section.

4. **Build the production site.**

   ```sh
   pnpm docs:build
   ```

   This catches MDX, frontmatter, component, icon, and configuration failures.
   It also produces the Pagefind search index.

5. **Exercise the reader journey.**

   Check the page from a sidebar entry, follow every local link, use search, and
   repeat at a narrow mobile viewport. Inspect the browser console.

</Steps>

## Writing rules

- Lead with the supported path, then explain alternatives.
- Put commands in repository-root context unless a preceding step changes
  directories.
- State prerequisites and expected output.
- Separate verified current behavior from roadmap ideas.
- Verify the production server as well as the build when changing deployment
  code. The pinned Node adapter's startup banner is incompatible with Astro
  7.2.3 and newer; the docs Dockerfile sets `ASTRO_NODE_LOGGING=disabled` to skip
  only that banner. A direct `node dist/server/entry.mjs` smoke run needs the
  same setting. Request/error logs remain enabled.
- Name the source file or subsystem when a statement is code-sensitive.
- Document failure semantics, irreversible steps, secret handling, and provider
  limits next to the happy path.
- Use tables for lookup and comparison, `<Steps>` for an ordered flow, and
  `<Aside>` only when the callout materially changes behavior.
- Avoid screenshots for changing settings screens unless layout is the subject;
  text remains searchable and survives UI updates.

<Aside type="tip">
Starlight automatically supplies search, heading anchors, previous/next links,
last-updated metadata, and GitHub edit links. Use those capabilities before
adding custom UI.
</Aside>

## Link and terminology conventions

- Internal content: `/docs/architecture/sync/`
- Heading: `/docs/architecture/sync/#incremental-sync`
- Source path: inline code such as `apps/api/src/sync/engine.ts`
- External documentation: use the authoritative project/vendor URL
- UI label: match the capitalization visible in the product

Use terms from the [Glossary](/docs/architecture/glossary/). If a new concept
appears in three pages, define it there.

## Diagrams

Use Mermaid code fences for architecture diagrams. The inline preview keeps
the page compact; **Open diagram** opens a larger view with zoom, **Fit**, and
**100%** controls. Scroll the diagram to reach details, and use Escape to return
to the page. The viewer follows the active theme and restores the inline
diagram before printing.

When changing a diagram, check its labels at actual size, both themes, and a
narrow viewport. Keep a descriptive heading immediately before it so its
enlarged view has a useful accessible name.

## Keep docs coupled to code

Update documentation in the same change when modifying:

| Code change | Documentation to review |
|---|---|
| Script, runtime, package manager | README, local setup, command reference |
| Environment variable or capability | `.env.example`, environment reference, deployment guide |
| Route or response | HTTP API, architecture/API, affected client flow |
| Schema or invariant | Data model, onboarding walkthrough, glossary |
| Provider mapping/limit | Provider guide and sync architecture |
| Timer, metric, log, dashboard | Observability runbook and self-hosting |
| Native module or build variable | Local setup, authentication, widget/release docs |

When a change adds a task route or provider projection, review the shared-task
guide, HTTP API, data model, sync architecture and affected provider page
together. Keep [capabilities and verification](/docs/operations/capabilities/)
and [release status](/docs/operations/releases/) explicit about implemented,
automatically tested, live-tested and deployed behavior. Preserve dated audits
as evidence rather than editing their historical results into current claims.

The docs build validates rendering and search generation. It does not compare
prose with the route registrar, prove that the documentation service deployed
the accepted revision, or certify provider/device behavior. Review those claims
against their named sources and inspect the published site after deployment.

## Review checklist

- [ ] The command was run from the directory shown.
- [ ] Version and environment claims match package manifests/config.
- [ ] New pages appear in the sidebar.
- [ ] Every internal link resolves under `/docs/`.
- [ ] Secret examples are placeholders and logs redact sensitive values.
- [ ] Limitations and failure behavior are explicit.
- [ ] `pnpm docs:build` passes.
- [ ] Desktop and mobile navigation were exercised without console errors.
- [ ] A code-sensitive page names the source of truth.

## Starlight configuration

The site uses explicit navigation, Pagefind search, edit links, last-updated
metadata, and the Node adapter. Reference the current upstream documentation
when changing configuration:

- [Starlight configuration](https://starlight.astro.build/reference/configuration/)
- [Authoring content](https://starlight.astro.build/guides/authoring-content/)
- [Sidebar navigation](https://starlight.astro.build/guides/sidebar/)
- [Built-in components](https://starlight.astro.build/components/using-components/)

Astro's Markdown defaults already include GitHub-flavored Markdown and smart
punctuation. Do not reintroduce removed `markdown.gfm` or
`markdown.smartypants` compatibility options.
