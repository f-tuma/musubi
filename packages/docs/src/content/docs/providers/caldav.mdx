The adapter at `apps/api/src/sync/adapters/caldav.ts` serves Apple/iCloud,
Nextcloud, Radicale, Fastmail, and other CalDAV servers. It synchronizes VEVENT
and VTODO collections in both directions, supports multiple accounts, and uses
Basic authentication rather than OAuth.

## Connect an account

<Steps>

1. **Configure credential encryption.**

   ```sh
   openssl rand -hex 32
   ```

   Put the result in the API environment:

   ```dotenv
   CALDAV_ENC_KEY=<64-hex-characters>
   ```

   Changing this key without migrating stored ciphertext makes existing CalDAV
   credentials and federated member tokens unreadable.

2. **Collect server credentials.**

   You need a CalDAV server URL, username, and password. Outside development,
   the URL must use HTTPS and every discovered or redirected target is checked
   against the private-address SSRF guard before credentials are sent. iCloud
   requires an Apple **app-specific password**, never the Apple ID password.

3. **Connect through Settings.**

   Credentials are stored in `caldav_accounts`, separate from Better Auth's
   OAuth `account` table. Passwords are AES-GCM encrypted before persistence.

4. **Inspect discovery and the first pull.**

   Use `LOG_LEVEL=debug` temporarily and correlate failures by `requestId`.
   Verify calendar discovery before diagnosing individual event mapping.

</Steps>

`providerFlavor()` labels an `icloud.com` server as Apple for display. The
underlying sync path remains CalDAV.

## Incremental reconciliation

When supported, the first pull uses WebDAV `sync-collection` without a token to
fetch the complete collection and obtain its cursor. Later pulls fetch only
changed resource URLs; deleted URLs become tombstones for both resource kinds so
the existing mapping is removed safely.

An expired token, unsupported report, malformed response, or missing next token
falls back to a complete depth-one `PROPFIND` listing and calendar multiget.
This avoids iCloud's `calendar-query` time-range requirement while keeping reset
sweeps complete. Unchanged ETags remain verified no-ops.

<Aside type="note">
CalDAV accounts appear as `musubi_sync_accounts{provider="caldav",status="unmonitored"}`.
Their credential table has no OAuth-style reconnect status. This inventory value
does not prove that a connection is healthy; use sync outcomes and structured logs.
</Aside>

## Event mapping

| CalDAV/iCalendar shape | Musubi behavior |
| --- | --- |
| Resource URL | Stable `externalId`; UID alone is not used |
| DATE `DTSTART` | All-day event at UTC midnight |
| Exclusive `DTEND` | Subtract one day for inclusive Musubi end |
| `RRULE`, `EXDATE`, `RDATE`, detached instances | Preserve and project recurrence exceptions |
| `TZID` + `VTIMEZONE` | Resolve instants and preserve the original zone on update |
| `VALARM` | Preserve alarm components while editing event or task fields |
| VTODO | Import and write task fields, UID, and ETag |
| ETag unchanged | No database write and no `updatedAt` bump |

Updates patch the existing calendar resource rather than replacing its complete
iCalendar payload. This keeps server-owned fields, detached recurrence
components, timezones, and alarms intact. If the recurrence rule itself changes,
stale detached instances are removed with the old series.

## VTODO task sources

Discovery reads `supported-calendar-component-set`. Only a collection advertising
`VTODO` becomes a task source; a VEVENT-only collection cannot accept a task.
`supportsTasks` identifies the resource kind, while current read/create/edit/delete
privileges govern each operation. Missing or ambiguous discovery properties are
an error, not evidence that a collection is empty or writable.

A task keeps its resource URL, iCalendar UID and ETag. Its home calendar controls
canonical content and completion; secondary collections receive provider
projections. Updates read the current resource, verify UID/ETag and patch changed
VTODO properties with conditional writes. `VALARM`, unrelated properties,
`VTIMEZONE` and unrelated components remain intact. Wire timestamps have iCalendar
second precision without truncating the canonical Musubi value.

Creation uses a deterministic resource address with `If-None-Match: *`. An
uncertain result can be reconciled by reading that address rather than issuing
another CREATE. Multiple provider projections for a recurring task are refused
until Musubi has a shared occurrence generator; existing home recurrence remains
supported.

See [Shared tasks](/docs/guides/shared-tasks/) for home permissions and delivery
receipts, and the [capability matrix](/docs/operations/capabilities/) for release
validation status.

## Calendar-level operations

Event objects use the typed `tsdav` client. Calendar lifecycle operations use
raw WebDAV so Musubi controls XML and Apple properties:

- `MKCALENDAR` for creation;
- `PROPPATCH` for display name and Apple calendar color; and
- `DELETE` for removal.

The adapter derives the calendar-home URL from an existing calendar. A
`207 Multi-Status` response to `PROPPATCH` is successful; a server that ignores
Apple's color property is non-fatal.

## Troubleshooting

### iCloud authentication fails

Generate a fresh app-specific password after confirming two-factor
authentication is enabled. Do not enter the normal Apple ID password.

### Discovery succeeds but no events arrive

Check the exact collection URL and whether the server permits depth-one
`PROPFIND`, `calendar-multiget`, or `sync-collection` on that collection.

### Property response is incomplete or ambiguous

`DavReadResponseError` exposes a safe `cause` with
`code="caldav-read-response-invalid"`, a bounded `reason`, `readKind`, counts or
HTTP/property statuses, and sometimes `hrefRelation`. Use those fields to locate
the failure without collecting XML, credential headers or private resource paths:

| Diagnostic | Meaning |
| --- | --- |
| `readKind="principal"` | Reading `current-user-principal` from the account resource |
| `readKind="home"` | Reading `calendar-home-set` from the principal resource |
| `readKind="discovery"` | Discovering collection types and supported components |
| `readKind="listing"`, `"multiget"`, `"sync"` | Listing or reading resource changes |
| `hrefRelation="different-path"` | The discovery response identifies a different resource path |
| `hrefRelation="different-query"` or `"different-origin"` | Discovery identity does not match the requested query or origin |

Discovery requires one authoritative resource response with complete required
properties. A collection's trailing-slash alias is accepted only with collection
or canonical-location evidence. Other path mismatches remain refused; do not
disable the identity fence to work around a failing server. Reproduce against a
disposable account and retain only sanitized diagnostics in public reports.

### Tasks are missing from a discovered calendar

Check that the collection explicitly advertises `VTODO` and grants current read
access. A display name, server brand or VEVENT support alone is insufficient.

### Every sync appears to rewrite everything

Inspect ETag preservation and reset-upsert behavior. A quiet, unchanged
full-fetch should not bump local timestamps or emit an external-sync nudge.

### Credentials became unreadable after deployment

Verify the deployment still has the original `CALDAV_ENC_KEY`. Restore that key
from the secret manager; guessing or regenerating it cannot decrypt existing
rows.

## Contributor checklist

- test against a generic CalDAV server and iCloud when feasible;
- preserve resource URLs, ETags, inclusive/exclusive dates, and DATE-typed
  exceptions;
- cover VTODO capability/privilege discovery, conditional task updates,
  deterministic-create reconciliation and preservation of unrelated properties;
- cover `207 Multi-Status` and ignored color-property behavior;
- never log Basic auth values, encrypted payloads, tokens, or full request
  bodies;
- verify incremental pulls and expired-token fallback; and
- run `pnpm check` plus a disposable-account round trip.
