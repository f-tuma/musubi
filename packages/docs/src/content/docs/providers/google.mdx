Google Calendar and Google Tasks use the adapter implemented in
`apps/api/src/sync/adapters/google.ts`. One Musubi user can connect multiple
Google accounts; every imported calendar retains the account that owns its
provider credentials.

Read [Sync engine architecture](/docs/architecture/sync/) first if you are
changing adapter code. This page focuses on Google-specific behavior.

## Configure the provider

<Steps>

1. **Create Google OAuth clients.**

   The API needs a Web client. Register this exact authorized redirect URI:

   ```text
   {BETTER_AUTH_URL}/api/auth/callback/google
   ```

   Native sign-in also needs platform-facing client identifiers compiled into
   the app.

2. **Set the server variables.**

   ```dotenv
   GOOGLE_WEB_CLIENT_ID=...
   GOOGLE_CLIENT_SECRET=...
   ```

   Better Auth requests offline access and explicit consent so Google returns a
   refresh token. The connection flow requests these scopes:

   ```text
   https://www.googleapis.com/auth/calendar.events
   https://www.googleapis.com/auth/calendar.calendarlist
   https://www.googleapis.com/auth/calendar.calendars
   https://www.googleapis.com/auth/tasks
   ```

   Web connections always include Tasks. The native connection dialog defaults
   **Include tasks** to enabled and can still omit the Tasks scope. Sign-in is a
   separate identity flow; it does not automatically grant calendar/task access.
   When availability is enabled, the connection additionally requests
   `https://www.googleapis.com/auth/calendar.events.freebusy`.

   Enable the Calendar and Tasks APIs in the Google Cloud project. Existing
   calendar-only grants do not gain Tasks access on refresh: reconnect the exact
   account with Tasks consent. An explicitly narrowed refresh grant is respected.

3. **Set the native build variables when testing the mobile flow.**

   ```dotenv
   EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID=...
   EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID=...
   ```

   Rebuild the development client after changing `EXPO_PUBLIC_*`; Metro cannot
   replace values compiled into native configuration.

4. **Confirm capability discovery.**

   ```sh
   curl http://localhost:7531/api/v1/server
   ```

   `syncProviders` should contain `google`. Then connect the account in
   Settings and inspect API logs using the response `x-request-id`.

</Steps>

See [Environment variables](/docs/reference/environment/#google) and
[Authentication](/docs/architecture/authentication/) for the full native and
Better Auth setup.

## Calendar mapping

- Calendars come from `users/me/calendarList`.
- A calendar is read-only unless Google reports `owner` or `writer`.
- Color is user-specific and comes from the `calendarList` entry's
  `backgroundColor`.
- Renaming or recoloring a linked calendar patches Google before Musubi updates
  its local mirror.

## Incremental sync

Google provides an unbounded `syncToken`:

1. the first pull paginates through the full event history;
2. the final page returns `nextSyncToken`;
3. later pulls send that token and receive only changes;
4. `410 Gone` means the cursor expired, so the adapter performs a reset pull and
   the engine reconciles the full result.

Persist the next cursor only after a successful pull. A partially consumed page
sequence must never advance it.

## Google Tasks sources

Each Google task list is a separate Musubi calendar source with
`supportsTasks=true` and `supportsEvents=false`. Google Calendar sources have
the opposite flags. A task is stored once in Musubi; its home calendar controls
editing and completion, and supported secondary calendars receive projections.
A Musubi membership does not change Google's own sharing permissions.

Task-list discovery requires the stored Tasks grant. Missing consent or a
task-specific authorization failure does not turn an incomplete task-list result
into an authoritative empty list or delete existing task sources. Account-wide
authentication failures remain errors and may require reconnecting.

Tasks have no Calendar-style collection sync token. Every task pull consumes all
pages, including completed, hidden and deleted entries, before reconciliation.
A partial read must not advance state or sweep missing tasks.

### Projection and delivery

| Field | Google Tasks projection |
| --- | --- |
| Title and notes | Writable task fields |
| Status | `completed` or `needsAction`; other Musubi phases project to `needsAction` |
| Due | Calendar day from the canonical UTC date; time is discarded |
| Priority, start, recurrence and partial progress | No writable projection in this adapter |

Google's `due` represents a scheduled calendar day, not an exact deadline.
Musubi compares supported fields against the accepted provider baseline so an
unchanged lossy projection does not erase richer canonical data. Assigned
Docs/Spaces tasks are readable imports but are refused as general task write
targets. These boundaries follow the [Google Task resource](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks).

Updates read the current task, require its accepted ETag, and send only changed
supported fields using `If-Match`. A conflict is shown in delivery status;
refresh before preparing another edit. See [Google's conditional PATCH guidance](https://developers.google.com/workspace/tasks/performance#using_patch_in_a_read-modify-write_cycle).

A lost CREATE response may mean Google created the item without Musubi receiving
its ID. That operation remains unconfirmed; automatic or manual retry cannot
blindly create another item. Local acceptance and confirmed provider delivery
are distinct outcomes. Multiple provider projections for a recurring task are
currently refused.

See [Shared tasks](/docs/guides/shared-tasks/) for home permissions, linking,
independent copies and delivery receipts, and the
[capability matrix](/docs/operations/capabilities/) for release validation status.

## Event mapping

| Google shape | Musubi behavior |
| --- | --- |
| `start.date` | All-day event at UTC midnight |
| Exclusive `end.date` | Subtract one day for Musubi's inclusive all-day end |
| Recurrence array | Preserve RRULE/EXDATE text on the series master |
| Cancelled item | Tombstone the mirrored event |
| Conference entry point | Store as the event URL |
| `htmlLink` | Deliberately ignored; it is a Google UI link, not the meeting |

`sanitizeRecurrence()` repairs provider quirks seen in received recurrence
rules. `toGoogleRecurrence()` keeps all-day `EXDATE` and `UNTIL` values
DATE-typed when pushing them back.

## Failure modes

### The account needs reconnecting

A revoked or unusable refresh token sets the account sync status to a reconnect
state. Reconnect that exact account; do not delete other accounts belonging to
the same provider.

### Calendars sync but task lists are missing

Check the exact account's stored OAuth grant and `sync.tasks.discovery_unavailable`
logs. Reconnect with Tasks consent when it is absent; a token refresh cannot
authorize a new scope. Verify that the Tasks API is enabled. Do not remove task
lists based on an incomplete discovery result.

### A full sync repeats

Look for a Google `410`, failed pagination, or a cursor that was not persisted.
A legitimate expired token causes one reset. Repeated resets indicate cursor
storage or token-refresh trouble.

### A calendar is unexpectedly read-only

Inspect `accessRole` in the Google Calendar List response. Subscribed holiday
calendars and calendars shared as `reader` are intentionally not writable.

### The OAuth option is missing

Check `GOOGLE_WEB_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, restart the API, then
inspect `/api/v1/server`. Native values alone do not enable server-side sync.

## Contributor checklist

When changing this adapter:

- preserve pagination and cursor atomicity;
- cover all-day inclusive/exclusive conversion in both directions;
- test recurring master, EXDATE, cancelled item, and `410` reset behavior;
- keep calendar-list colors separate from calendar resources;
- cover complete task pagination, missing/narrowed Tasks grants, date-only and
  two-state projection preservation, ETag conflicts and uncertain CREATE;
- use the shared OAuth refresh/encryption path;
- record provider failures with bounded metric labels; and
- run `pnpm check` (including the fake Google `410`/pagination server),
  `pnpm test:provider-db` when touching OAuth lifecycle, then a real
  sandbox-account round trip when credentials are available.

<Aside type="note">
The automated repository checks exercise Google pagination, cursor reset,
partial-page discard and OAuth retry/rotation against local fakes. They do not
provide a live Google integration environment. Treat a provider sandbox smoke
test as part of release validation.
</Aside>
