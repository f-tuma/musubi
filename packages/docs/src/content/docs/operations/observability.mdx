Musubi exposes Prometheus metrics on a private listener and writes structured
JSON logs to stdout/stderr. The implementation lives in
`apps/api/src/metrics.ts`; dashboards and alerts live under `ops/`.

## Metrics endpoint

| Property | Value |
|---|---|
| Listener | Separate from the public API |
| Port | `METRICS_PORT`, default `9464`; `0` disables it |
| Path | `GET /metrics` |
| Bind address | `0.0.0.0` |
| Prefix | `musubi_` |
| Constant label | `service="api"` |

The bundled Compose files do not publish this port to the host. Scrape it from a
trusted Docker network:

```yaml
scrape_configs:
  - job_name: musubi-api
    static_configs:
      - targets: ["musubi-api:9464"]
```

Keep the job name `musubi-api`; the shipped dashboards and alert rules expect
it.

## Metric catalog

### HTTP

| Metric | Type | Labels |
|---|---|---|
| `musubi_http_requests_total` | counter | `method`, `route`, `status` |
| `musubi_http_request_duration_seconds` | histogram | `method`, `route`, `status` |
| `musubi_http_requests_in_flight` | gauge | `method` |

Routes use registered Express patterns, never concrete URLs. UUIDs and invite
tokens therefore do not become high-cardinality labels.

### Provider sync

`musubi_external_sync_failures_total{stage,provider}` counts bounded failure
classes. `stage` is one of `account`, `discovery`, `push`, or `scheduler`;
provider is a known provider name, `all`, or `unknown`.

Task delivery failures also contribute to the bounded `stage="push"` counter.
That counter does not distinguish task/event queue depth or prove delivery of an
individual mutation.

### Delivery queues

| Metric | Scope |
| --- | --- |
| `musubi_event_outbox_operations{provider,status}` | Unresolved event operations at the last successful event-drainer refresh |
| `musubi_event_outbox_oldest_seconds{provider,status}` | Age of the oldest unresolved event operation at that refresh |

These metrics describe **events only**. v0.2.2 does not export task-outbox backlog,
oldest age or collector-success/freshness gauges. `musubi_tasks` counts task
inventory, not pending provider delivery.

The event drainer resets its labeled gauges before applying the returned rows.
An empty result therefore removes series rather than emitting an explicit zero.
The same absence can occur before the first refresh or when the scheduler is not
running. Neither missing series nor a healthy `musubi_usage_snapshot_success`
proves an empty event/task queue: the usage collector does not read outboxes.
Treat a flat dashboard as inconclusive until queue state and collection freshness
have been independently verified.

Use authorized delivery receipts for individual writes. A read-only database
aggregate can verify backlog without collecting task/event content; obtain the
deployment owner's permission before querying production. Keep addresses,
payloads, provider validators and raw errors out of public reports.

`musubi_scheduled_task_skips_total{task}` increments when `cleanup` or
`external_sync` (also `event_outbox`, `reminders` or `notifications`) is still
running at its next tick. One increment means overlap
was prevented, not that two runs executed. Investigate duration, provider
latency, and interval sizing; the shipped `MusubiScheduledTaskOverlap` alert
fires on any increase.

### Usage snapshot

The API computes current-state gauges from PostgreSQL and caches the snapshot for
60 seconds:

| Metric | Meaning |
|---|---|
| `musubi_users_total` | Non-federated local users |
| `musubi_events_total` | Live events |
| `musubi_calendars_total` | Calendars |
| `musubi_active_users` | Users with a valid session |
| `musubi_active_sessions` | Non-expired sessions |
| `musubi_sync_accounts{provider,status}` | Connected credential/provider accounts |

CalDAV credentials live outside Better Auth and have no OAuth account status, so
they appear with `status="unmonitored"`. Use the failure counter and logs for their
health.

### Process and live connections

`prom-client` Node/process defaults are exported under the same prefix. SSE
gauges are per process:

- `musubi_sse_connections`;
- `musubi_sse_users`; and
- `musubi_process_*` / `musubi_nodejs_*`.

The supported deployment has one API replica, so these gauges describe the
whole service. A future coordinated multi-replica design would need to aggregate
them with `sum(...)`.

## Structured logs

Every completed request emits `http.request.completed` with:

- `method`, registered `route`, `status`, and `durationMs`;
- `requestId`, also returned as the `x-request-id` response header; and
- `userId` when authenticated.

Status determines level: 5xx is `error`, 4xx is `warn`, everything else is
`info`. Provider-sync debug logs add per-account/per-calendar counts and timing
when `LOG_LEVEL=debug`.

<Aside type="caution">
Do not add request bodies, passwords, OAuth codes, refresh tokens, CalDAV
credentials, invite tokens, or member tokens to logs. A request ID is the safe
join key between client reports and server activity.
</Aside>

## Shipped operations assets

| Path | Purpose |
|---|---|
| `ops/prometheus/musubi-alerts.yml` | Target-down, 5xx, and provider-sync alerts |
| `ops/grafana/musubi-usage-dashboard.json` | Users, calendars, events, sessions, accounts, sync and SSE |
| `ops/grafana/musubi-api-dashboard.json` | Throughput, failures, latency and process health |
| `ops/grafana/musubi-logs-metrics-dashboard.json` | Combined Prometheus and Loki investigation |

Import dashboard JSON through Grafana's **Dashboards → New → Import**. Select the
Prometheus/Loki data sources requested by the template variables.

### These assets are checked against the code

Observability fails quietly by nature. A panel whose metric was renamed draws an
empty graph, which looks exactly like a healthy system; an alert whose metric was
renamed simply never fires, and a rule that never matches is indistinguishable
from a rule that never had cause to. Both are discovered during the incident they
existed to catch.

So the files above are read as a contract in CI, under the **Observability** job:

- `apps/api/src/metrics.test.ts` fails if any series a dashboard panel or an
  alert rule reads is missing from the registry, and if an alert has no
  `severity` label or `summary` annotation — one nothing can route, the other a
  page that says only the rule's name. It also pins the `route` label to
  registered Express patterns, which is what keeps label cardinality finite and
  invite tokens out of the metric store.
- `packages/config/src/logger.test.ts` covers the properties that make the logs
  usable: one JSON object per line, warnings and errors on stderr, and the
  redaction that makes `logger.error("failed", { error })` safe to write without
  first inspecting what the object carries.
- `promtool check rules` loads `musubi-alerts.yml` the way Prometheus would.

Renaming a metric is allowed. Renaming it without updating `ops/` is not.

Useful queries:

```text
# State growth is derived from stored gauge history
delta(musubi_events_total[7d])
delta(musubi_users_total[24h])

# Connected external providers
sum by (provider) (
  musubi_sync_accounts{provider=~"google|microsoft|caldav"}
)

# API 5xx ratio
sum(rate(musubi_http_requests_total{status=~"5.."}[5m]))
/
sum(rate(musubi_http_requests_total[5m]))
```

## Incident triage

<Steps>

1. **Define the blast radius.**

   Check API reachability, 5xx ratio, latency, database availability, sync
   failures, and whether only one provider/account is affected.

2. **Capture a request ID.**

   Ask for the `x-request-id` from the failing response, or reproduce once. Find
   the same ID across request, auth, handler, sync, and error log entries.

3. **Separate local persistence from provider delivery.**

   Calendar-level provider mutations are attempted before the local mirror
   changes. Accepted event and task mutations persist provider work in durable
   outboxes; HTTP success is local acceptance, not proof of remote delivery.
   Inspect the authorized delivery receipt. A lost CREATE response may remain
   unconfirmed and cannot be blindly replayed. See
   [Sync failure semantics](/docs/architecture/sync/#write-path-and-failure-semantics)
   and [Shared tasks](/docs/guides/shared-tasks/).

4. **Inspect the account and cursor.**

   Determine provider, exact connection, `syncStatus`, calendar cursor/window,
   last successful sync, and whether a legitimate reset is in progress.

5. **Enable debug logs briefly.**

   Set `LOG_LEVEL=debug`, reproduce one bounded operation, then restore the
   production level. Never collect secrets while increasing detail.

6. **Verify recovery.**

   Confirm a subsequent pull converges database, provider, and client cache.
   Record the alert, request ID, provider/account scope, cause, and prevention.

</Steps>

## Current scaling boundary

The scheduler, cleanup timers, SSE registry, rate limiter, and metrics registry
are process-local. Musubi therefore enforces **one active API process per
database**:

- `apps/api/src/singleton.ts` holds a dedicated, session-scoped PostgreSQL
  advisory lock for the process lifetime;
- a second API pointed at the same database exits before listening;
- both shipped Compose files declare `deploy.replicas: 1`; and
- losing the lock connection terminates the process instead of silently serving
  with an invalid coordination assumption.

Cleanup and external sync additionally use an in-process single-flight guard.
If one run exceeds its interval, the next tick is skipped and observable through
logs plus `musubi_scheduled_task_skips_total`.

True horizontal scaling still requires:

- coordinate or singleton-run scheduled jobs;
- use shared pub/sub for cross-replica SSE delivery;
- replace the in-memory rate limiter for a global policy; and
- aggregate per-instance metrics.

Do not remove or bypass the singleton lock until those pieces exist. A database
alone does not coordinate these in-memory behaviors; its advisory lock currently
prevents the unsupported topology rather than making it safe.

## Product observability

Import `ops/grafana/musubi-product-dashboard.json` and select the Prometheus
source. It provides sessions by device, OS and browser; task inventory by phase,
RFC priority and home provider; authenticated feature API traffic; provider
accounts, discovered calendar capabilities, sync volume, failures, latency and
unresolved event deliveries. The existing API and logs dashboards remain useful
for investigating a change in those product signals.

### What the numbers mean

- `musubi_sessions_by_client{device,os,browser}` counts **unexpired login
  sessions**, not online users or physical devices. Classification uses coarse
  User-Agent patterns. Desktop-mode iPads can look like Macs; Android tablets
  without a tablet marker can look like phones; native apps may be `unknown`.
- `musubi_active_users` remains the compatibility name for users with valid
  sessions. It is **not DAU/WAU/MAU**. `musubi_sse_users` measures currently
  connected live-update users, including background tabs.
- `musubi_tasks{status,priority,provider}` counts non-deleted tasks, including
  imports, completed and cancelled tasks. Priority follows RFC bands: high 1–4,
  medium 5, low 6–9, none 0. Provider is the home calendar source, not every
  calendar the user can access.
- `musubi_product_requests_total{feature,method,outcome,device}` counts
  authenticated requests to events, tasks, calendars, pages, availability and
  reminders. It includes background refresh and federated callers. Successful
  write responses are useful feature traffic, but retries/no-ops may count again.
  It does not measure screen views, Kanban versus list adoption, engagement,
  unique human actions, cohorts or retention. Inventory growth is **net change**,
  not the number of creations: deletion and imports affect it too.
- `musubi_provider_calendars{provider,state,events,tasks}` counts discovered
  sources and their support flags. It does not claim recent successful sync.
  CalDAV linked accounts now use `status="unmonitored"`, because their account
  table does not record OAuth-style reconnect state. Credential accounts are
  login accounts, not connected calendar providers.
- `musubi_sync_runs_total{provider,outcome}` and
  `musubi_sync_run_duration_seconds` observe completed account sync attempts.
  Discovery failures before an account is invoked remain in
  `musubi_external_sync_failures_total`. Received-object counters count persisted
  calendar batches, including unchanged objects and repeated full reads.
  They are throughput, not unique objects or creation counts.

Counters begin when this version starts and reset on API restart. Use `rate` or
`increase`, not subtraction, for counters. Low traffic or no sync attempts can
produce no series rather than zero; this must not be interpreted as proof of
healthy integrations. Database inventory gauges are cached for 60 seconds and
are **not counters**, even legacy names ending in `_total`.

### Collection health and data boundaries

All inventory collectors share one in-flight, read-only, repeatable-read
snapshot. A dedicated single-connection pool bounds connection acquisition to 1.5 seconds,
each statement to one second, and the collector wait to five seconds. A failed refresh preserves
last-good inventory; a cold failure exports no labeled inventory and `NaN` for
scalar inventory. `musubi_usage_snapshot_success` and
`musubi_usage_snapshot_timestamp_seconds` distinguish stale data from healthy
zero counts. Failed refreshes back off for 60 seconds. Alert on collection health
before drawing product conclusions from stale inventory.

No email, user/session ID, IP address, event/task title, calendar name, token,
provider URL or raw User-Agent is exported as a metric label. Labels are coarse,
bounded categories. Session classification is performed in PostgreSQL; only
aggregated family counts are returned. This adds no third-party analytics SDK,
fingerprinting, event payload collection or browser tracking endpoint. The
Prometheus endpoint must remain on the trusted monitoring network.

This version deliberately does not turn background API requests into a claimed
human-retention metric. Reliable adoption funnels and DAU cohorts require a
separately defined, explicit user-interaction event model and retention policy.

### Prometheus setup

`ops/prometheus/prometheus.yml` is a usable configuration example for the Compose
service `api` on the same private Docker network. Mount it as
`/etc/prometheus/prometheus.yml` and mount `musubi-alerts.yml` alongside it. Other
deployments must adjust the target. The metrics port is 9464 by default; reflect
any `METRICS_PORT` override in the scrape target. A value of 0 disables export.
The example scrapes every 30 seconds and evaluates alerts every 30 seconds.

Choose retention explicitly on the Prometheus process, for example
`--storage.tsdb.retention.time=90d`, and size disk based on actual ingestion.
Changing retention does not recover historical data. Keep one API target per
Musubi database: the application currently supports one API process per database.
Do not sum duplicate scrape targets for the same database inventory. Isolate
separate deployments using separate Prometheus data sources or job names and
adapt the dashboard job selector accordingly.

The supplied rules also cover stale product inventory, provider reconnection and
old pending/retry event deliveries. Rules alone do not send notifications:
configure your Alertmanager and receivers. Validate before rollout with
`promtool check config /etc/prometheus/prometheus.yml` and
`promtool check rules /etc/prometheus/musubi-alerts.yml`. Import dashboards into a
Grafana instance with access controls; importing a dashboard does not deploy or
activate the collector on an existing API image.

`EXTERNAL_SYNC_INTERVAL_MIN` also controls scheduled outbox recovery. A positive
value enables the startup drain and the 15-second event/task outbox worker as
well as provider polling. A value of `0` disables those scheduled recovery
paths; request-triggered delivery wakeups remain, but they do not establish that
retained work will drain after a restart. Confirm this setting through permitted
deployment metadata; do not expose environment secrets during an audit.

### Deployment and receiver verification

Repository validation proves that the shipped assets are syntactically valid and
refer to implemented metrics. It does not establish which rules, retention or
receivers are installed in a deployment. Inspect both Prometheus rules and
Grafana-managed rules; one engine can have no rules while the other has active
configuration. An `inactive`/`Normal` rule is not a successful notification test.

The production read-only review on 5 October 2026 observed a healthy API scrape,
a successful usage snapshot, and two Grafana-managed rules in `Normal` state.
Prometheus reported no alert rules. Receiver delivery was **not tested**, and
these observations did not certify empty delivery queues or successful live
shared-task provider round trips. Operational acceptance still requires an
authorized QA notification received by its intended recipient. Do not trigger
alerts or change routing merely to inspect an existing deployment.
