This is the current capability summary for **v0.2.2**, reviewed on **5 October
2026**. Use it with the provider guides and linked contracts. Dated audits retain
the scope tested on their date; an older “not supported yet” statement does not
override a later accepted implementation.

## Reading the evidence

- **Implemented** describes the bounded contract in the released source. An
  enabled flag still requires fresh ownership, access, native identity and
  version proof for the particular operation.
- **Automated** identifies synthetic HTTP, database or client regression
  evidence. A fake provider or browser fixture does not certify a live account.
- **Live** identifies the real-provider operation and date that were verified.
  Those fixtures do not certify every tenant, server or calendar shape.
- **Deployed** distinguishes a released implementation from independently
  verified runtime activation. Public production health reported **0.2.2** on
  5 October; private Core settings were not read. **Gate not verified** below
  does not mean disabled, enabled or broken.
- **Deferred / limits** names unsupported implementation scope separately from
  remaining device, delivery or operational acceptance.

<Aside type="caution" title="Version is not feature acceptance">
An HTTP 200 health check proves that the API responds with its reported version.
It does not prove provider permissions, applied migration history, matching image
digests, empty delivery queues, guest email delivery or any particular Core gate.
No new Core gate was activated as part of this documentation review.
</Aside>

## Outlook / Microsoft calendar

Specialized organizer, attendee and occurrence/series content or time operations
require the connected owner's verified **default calendar** and current OAuth
identity. Personal creation/deletion retain the owned-calendar and mapping proof
specified in their linked contracts. Recurring operations also require a complete
native family. Finite families are bounded to **366
original occurrences within 730 days**. Provider-expanded imports and canonical
tracked families retain their representation; a supported write does not silently
adopt one as the other. Online meetings, attachments, shared/delegated copies and
ambiguous or incomplete native evidence are excluded from these specialized paths.

## Shared tasks and release clients

Tasks have one identity and home calendar, revision-fenced mutation receipts and
multiple readable memberships. **Only home-calendar `editTasks` authority permits
content changes or completion.** A secondary membership can authorize linking,
unlinking that membership or an independent copy; it does not confer completion
authority. Provider-native permissions are never changed by a Musubi link.

## Operational acceptance still open

The released source includes the implementations above. Remaining production and
device work must be tracked as acceptance or diagnostics, rather than relabelled
as missing code:

- Record exact deployed API/web image revisions and digests, the applied database
  migration journal and privacy-safe delivery queue counts/freshness. Public
  version and a successful startup migration log do not establish those facts.
- Reproduce the remaining CalDAV discovery failure using an authorized account
  or a sanitized response fixture; keep resource-identity checks fail closed.
- Run two-user shared-task acceptance and real Google/CalDAV delivery readback.
  Verify final native login/restart, task create/edit/complete/share, session
  boundaries and delivery UI on devices. The iPad launch alone closes none of
  those cases.
- Verify task/event queue monitoring freshness and alert receiver delivery with
  an authorized test. Existing normal alert evaluations are not a delivery test.

Do not enable a deferred Core gate or alter production solely because a path has
automated or historical live evidence. Runtime configuration changes and actual
provider writes require the operator's explicit scope and approval.
