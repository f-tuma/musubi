### Current database and delivery boundary

The source API migration journal has 88 entries, ending at
`0087_project_news` (index 87); `0086_sync_scheduling` precedes it. The actual
production journal remains unverified. Migration 0087 deliberately removes the
former SQL announcements table. Product news now comes from the shared root
`news.json` through cached, validated public GitHub reads. There is no per-server
announcement editor or allowlist. Do not run a pre-transition API against this
contracted schema; see [project news](https://github.com/f-tuma/musubi/blob/main/docs/project-news.md).

The encoder source default is ON. Before admitting new v1 operations, every
actual API, delivery worker and custom outbox consumer needs the current decoder
and exact pinned codecs. Stop old processes first, run one API replica, and
acquire its singleton lock before migration and listening.
`SYNC_OPERATION_V1_ENCODER_ENABLED=false` affects future admission only; it
neither converts nor stops existing v1 operations and does not make old workers
safe. Decoder-only consumers preserve v1 rows on HOLD; delivery needs the pinned
codecs.

`EXTERNAL_DELIVERY_RECOVERY_MODE=independent` is the default: event/task/move
recovery runs at startup and every 15 seconds even with provider polling at zero.
Explicit `legacy` couples background recovery to positive polling; `disabled`
stops background recovery. Request wakeups remain active in every mode. These
settings are not write kill switches. Recovery needs maintenance with public
writes blocked and all API/consumer processes stopped. An older Graph reader
can resume destructive window sweeps; an image switch is insufficient rollback
evidence for coverage, persisted v1 operations or the contracted news schema.

### Current publication contract

The publication workflow takes the full approved `expected_source_sha` and
version. It requires main and the matching captured/checkout SHA, and reuses the
completed **exact trusted main-push Quality run**. The contract is **nine
publication jobs plus proof of all 21 actual Quality jobs**; publication does not
rerun Quality. The pinned proof is checked again immediately before the fresh
non-force deployment tag. See the
[current publication and read-only verification contract](https://github.com/f-tuma/musubi/blob/main/docs/releases/publication.md).

API/web version tags and `latest` move before the Git tag; tag creation may start
deployment before the GitHub release body succeeds. Reconfirm the actual
operator-controlled trigger and mutable-image consumers, and establish approved
maintenance, backup and old-writer stop before dispatch. The workflow does not
enforce Dokploy's stop-first or API→web sequence. After an uncertain push or
release reply, reconcile actual state read-only; do not delete, force, recreate,
adopt an existing tag or blindly rerun publication.

## Mobile task compatibility

Since 0.2.2, task writes need the mutation protocol shipped by 0.2.2 or newer
clients, including create, edit, completion, priority and deletion. Older clients
keep task reads and compatible calendar/event features. Legacy task-write routes
return HTTP 426 before provider preflight or local commit, regardless of the
version header supplied.

Current clients use `/api/v1/task-mutations`. An API predating 0.2.2 has no such
namespace and returns 404; clients retain the draft and never retry through a
legacy writer. Global client and federation peer minimums remain 0.2.0.

The 0.2.2 origin-isolation transition required signing in again: legacy ambiguous
credentials/cache were cleared before authentication. Credentials and local
content remain isolated by full server origin and current user. Verify the actual
upgrade and login/restart behavior on each final signed candidate rather than
assuming a new release always needs reauthentication. There is no OTA update
channel: users must install the store/TestFlight build. During a distribution
gap, use the current web client for task changes.

For device acceptance, record the installed product version and platform build
number, then verify login after a process restart, ordinary and shared-task
writes, offline/reconnect, provider delivery and supported OS reminders. Opening
the app alone does not complete these checks.

## Database upgrade and recovery

Compare the actual production journal with the final candidate; a public API
version is not journal evidence. The audited source ends at 0087. The earlier
0.2.2 upgrade added 0079–0084 after the 0.2.1 journal ending at 0078; its task
home/membership, revision and durable-delivery boundary remains relevant. The API
acquires its singleton lock before running the migrator and listening. Stop the
previous API and all old consumers before replacing them and run one replica.

<Aside type="caution" title="An image-only downgrade is unsafe">
After migration 0080, the older task writer does not maintain canonical
memberships, revision checks or task delivery. Migration 0087 also removes the
old announcements table; persisted v1 operations and Graph read coverage impose
additional decoder/reader requirements. Recovery needs a compatible forward fix,
or the exact prior images together with a verified matching pre-upgrade database
restore and stopped writers. Restoring the database cannot undo changes already
delivered to a provider. Do not rewrite migration history or blindly replay
uncertain creates.
</Aside>

Before an upgrade, retain a verified restore, prior image digests, the migration
journal and aggregate data/queue counts. Afterward, compare the journal and
preservation evidence and run authenticated task/event smoke tests with an
approved test account. Keep private data and credentials out of release records.

Use the [current production runbook](https://github.com/f-tuma/musubi/blob/main/docs/releases/0.2.12-readiness.md)
for preparation and recovery. The historical
[0.2.2 deployment record](https://github.com/f-tuma/musubi/blob/main/docs/releases/0.2.2-deployment.md)
retains that release's migration details and content-free SQL aggregates. Follow

## Keep activation separate

Preserve existing Core gates during an upgrade. Historical 0.2.0 activation
examples are not settings to copy into a new deployment. Do not newly enable
iCloud attendee RSVP, provider reminders, CalDAV alarms or Google availability
without their accepted live/device evidence and an operator decision.

Shared-task writes have no rollout flag. Disabling scheduled external sync does
not prevent request-triggered task delivery and is not a task-write kill switch.
A local committed receipt proves the Musubi transaction; inspect destination
delivery separately. See [shared tasks](/docs/guides/shared-tasks/).

## Release record checklist

For each release, retain:

- accepted source SHA, exact main-push Quality proof, nine-job publication receipt
  and published API/web digests;
- actual running digests/revisions and the pre/post migration journal;
- backup/restore evidence and content-free preservation/queue counts;
- existing capability decisions, without secret configuration values;
- exact Android/iOS artifacts and installed device versions;
- authenticated smoke and independent provider readback results;
- explicitly deferred checks and their owner-approved rollout decision.

Update this record from observed results. Preserve dated audits as historical
evidence rather than treating them as the current feature list.
