## Mobile task compatibility

Every task write against the 0.2.2 API needs the 0.2.2 client, including create,
edit, completion, priority and deletion. Older clients keep task reads and
compatible calendar/event features. Their legacy task writes return HTTP 426
before provider preflight or local commit.

Current clients use `/api/v1/task-mutations`. On an older API this namespace is
absent and returns 404; clients retain the draft and never retry through a
legacy writer. Global client and federation peer minimums remain 0.2.0.

Installing the mobile update requires signing in again. Credentials and local
content are isolated by full server origin and current user; legacy ambiguous
credentials/cache are cleared before authentication. There is no OTA update
channel: users must install the store/TestFlight build. During a distribution
gap, use the current web client for task changes.

For device acceptance, record the installed product version and platform build
number, then verify login after a process restart, ordinary and shared-task
writes, offline/reconnect, provider delivery and supported OS reminders. Opening
the app alone does not complete these checks.

## Database upgrade and recovery

The 0.2.1 database journal ends at 0078. The new release adds 0079–0084, including
task home/memberships, revision admission, durable delivery and fork outcomes.
The API acquires its singleton lock before running the migrator and listening.
Stop the previous API before replacing it and run one replica.

<Aside type="caution" title="An image-only downgrade is unsafe">
After migration 0080, the older task writer does not maintain canonical
memberships, revision checks or task delivery. Recovery needs a compatible
forward fix, or the exact prior images together with a verified pre-upgrade
database restore. Restoring the database cannot undo changes already delivered
to a provider. Do not rewrite migration history or blindly replay uncertain
creates.
</Aside>

Before an upgrade, retain a verified restore, prior image digests, the migration
journal and aggregate data/queue counts. Afterward, compare the journal and
preservation evidence and run authenticated task/event smoke tests with an
approved test account. Keep private data and credentials out of release records.

The maintained [0.2.2 deployment and recovery runbook](https://github.com/f-tuma/musubi/blob/main/docs/releases/0.2.2-deployment.md)
contains migration details and content-free SQL aggregates. Follow
[self-hosting](/docs/guides/self-hosting/) for stack setup and
[observability](/docs/operations/observability/) for queue evidence.

## Keep activation separate

Preserve existing Core gates during an upgrade. Historical 0.2.0 activation
examples are not settings to copy into a new deployment. Do not newly enable
iCloud attendee RSVP, provider reminders, CalDAV alarms or Google availability
without their accepted live/device evidence and an operator decision.

Shared-task writes have no rollout flag. Disabling scheduled external sync does
not prevent request-triggered task delivery and is not a task-write kill switch.
A local committed receipt proves the Musubi transaction; inspect destination
delivery separately. See [shared tasks](/docs/guides/shared-tasks/).

## Release record checklist

For each release, retain:

- accepted source SHA and published API/web digests;
- actual running digests/revisions and the pre/post migration journal;
- backup/restore evidence and content-free preservation/queue counts;
- existing capability decisions, without secret configuration values;
- exact Android/iOS artifacts and installed device versions;
- authenticated smoke and independent provider readback results;
- explicitly deferred checks and their owner-approved rollout decision.

Update this record from observed results. Preserve dated audits as historical
evidence rather than treating them as the current feature list.
