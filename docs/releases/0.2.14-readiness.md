# Musubi 0.2.14 preparation and acceptance

Preparation snapshot: 3 November 2026. Publication and runtime acceptance are
recorded separately after execution.

## Candidate

Prepared API/web maintenance release; **not published or deployed**. The
implementation is [PR #398](https://github.com/f-tuma/musubi/pull/398), merged as
`990e601f6a4f836ee672bfd27490009ab35ef651`. Publication must use the final
version/notes merge commit and its own successful trusted main-push Quality run,
not the implementation PR's checks or an earlier main commit.

- Product/API version: 0.2.14. Client and peer minimums: 0.2.0.
- Existing mobile apps remain compatible. No EAS/store build is part of this release.
- No schema changes relative to 0.2.13: 88 migration entries, ending at 0087.
- API/web include the merged support-contact and service email-branding changes.
  The public website's operator/privacy changes were published separately.
- [English release notes](0.2.14-notes.md) are the publication workflow's source body.

## Verified source behavior

The implementation's 21 CI checks passed and independent review approved the
complete change. Its authenticated running API/PostgreSQL/loopback DAV test
imports 213 events across nine collections, confirms all ten work rows, preserves
exact pending generations and refuses partial apply/ACK after a later batch
fails. JSON scenarios exercise the actual waiter, coordinator, validator and DAV
client, including 100/100/5 native object batches.

Read-only native diagnostics accepted the two CDATA-affected responses and
completely validated both oversized collections in bounded batches. This is
structural/provider evidence, not a claim that the production engine imported
or acknowledged the previously failing collections. Private support-account
identifiers, credentials, event contents and native XML are excluded here.

## Publish once after approval

Set `MUSUBI_RELEASE_SOURCE_SHA` to the exact approved 40-character main commit.
The following command is the publication/deployment boundary; do not execute it
as a preparation check:

```sh
gh workflow run docker-publish.yml \
  --repo f-tuma/musubi --ref main \
  -f version=0.2.14 \
  -f expected_source_sha="$MUSUBI_RELEASE_SOURCE_SHA"
```

Record the returned/observed publication run identity once. The existing workflow
builds API and web for amd64/arm64, moves version/`latest` indexes, creates a fresh
tag at the pinned source and creates the GitHub release. Tag creation can start
Dokploy before the release body completes; mutable-image consumers can react
even earlier. Keep the existing automation in place and verify its real result.

After an uncertain dispatch, push or release reply, reconcile actual run, tag,
release, registry and deployment state read-only. Never blindly repeat the
publisher, force/delete/recreate a tag or adopt another publisher's release.

## Recovery

Preserve the accepted 0.2.13 API/web immutable digests and current database backup
before release. No migration is added here, but a rollback still requires the
existing single-writer/stop-first discipline and current queue/accepted-write
evidence. Prefer a reviewed forward fix. Do not restore an old database, clear
cursors/queues, weaken guards or replay uncertain writes merely to hide an
import failure. A rollback can reintroduce the iCloud bugs fixed by this release.
