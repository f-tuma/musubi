# Musubi v0.2.2 release preparation

Prepared on 2026-10-05. This document prepares the release; it does not record a
published tag, a store submission or a completed production deployment.

## Scope and artifacts

API, web and native clients declare **0.2.2** from the root manifest and shared
`PRODUCT_VERSION`. Global client and federation peer minimums remain **0.2.0**.
The existing 0.2.0 wire-contract baseline is retained.

This release includes shared tasks with home-calendar authority, source-scoped
provider projections, revision checks, durable delivery and replay-safe
independent copies; the web design-system migration and notification centre;
Google/CalDAV recovery fixes; and supported Outlook operations developed since
0.2.1. Provider-specific operations remain limited by capability and current
production gates. New Microsoft To Do live task links are excluded.

- [User-facing release notes](0.2.2-notes.md) are added to the GitHub release by
  the publication workflow; a concise announcement is installed by migration 0084.
- [Deployment, migration and recovery](0.2.2-deployment.md) covers the stop-first
  API upgrade, a verified database restore and provider reconciliation.
- [Mobile build and rollout](0.2.2-mobile.md) covers store builds and the mixed
  client/API period. A new mobile build is needed for every task write.

## Source acceptance

PR [#331](https://github.com/f-tuma/musubi/pull/331) contains the shared-task
candidate and release preparation. Before merging, all Quality checks must pass
on its final head, including the v0.2.1-to-0.2.2 PostgreSQL upgrade fixture.
Publication reruns Quality against the accepted `main` revision.

Local preparation verifies matching versions, native configuration and listing
validation, release announcement ordering, preservation of task identifiers,
provider validators and existing news/read markers, and migration idempotence.
Mocked/unit/browser coverage does not certify live provider or device behavior.
Store signing access, real iOS listing, native artifacts and physical-device
checks remain release operator evidence.

## Production decision

The known production entry points are `https://musubi.pro`,
`https://dokploy.frgtn.cz` and `https://grafana.frgtn.dev`. A public product
version is not proof of the deployed revision or database state. Read-only
operator access has not yet established the running image digests, migration
journal, gate values or a verified backup. Record those before switching API.

If live provider/device checks are intentionally deferred, record that decision
and the temporary loss of task writes in old mobile apps. A green CI result does
not remove these two operational risks. Preserve the current Core gates.

## Publication when accepted

1. Merge the accepted, green release PR into `main` and record that exact SHA.
2. Prepare the maintenance window and verified backup. Inspect/pause Dokploy's
   tag trigger until the stop-first deployment is ready.
3. Verify that `main` still equals the recorded accepted SHA; if it advanced,
   review and accept that newer revision before publication. From the accepted
   `main` revision, dispatch the existing **Publish Docker
   images** workflow with `version=0.2.2`. This is an actual publication action:
   it creates API/web AMD64+ARM64 manifests, then tag `v0.2.2`, which signals
   Dokploy. Do not create the tag separately.
4. Record API/web manifest digests and release SHA, perform the deployment
   runbook and smoke checks, then distribute the tested matching native builds.

Operator command after the above prerequisites are accepted:

```sh
gh workflow run docker-publish.yml --repo f-tuma/musubi --ref main -f version=0.2.2
```

Retain a private release record containing the exact source SHA, image digests,
pre/post migration journal, backup path and restore result, current gate values
without secrets, Android/iOS build IDs and build numbers, smoke-test outcomes,
and any explicitly deferred live/device checks. Do not commit tokens, database
content or private task/event text to this document.
