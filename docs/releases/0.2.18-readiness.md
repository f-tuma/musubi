Status: candidate only. This file records version and source facts, not
operational receipts. Publication, deployment, backup and runtime observations
have not been performed here. Each needs its own evidence, kept outside this
file.

## Scope

This is an API/web maintenance release for a delete/update conflict found by
the 0.2.17 mixed-provider write check. Take an event created in a Musubi
calendar and copied to Outlook, iCloud and Google calendars. Its delete was
refused with `409 provider-conflict`, and every later retry was refused too.

The cause was a stale stored copy version:

- A copy whose calendar is not the event's origin never refreshed its stored
  provider version after create.
- Outlook changes an event's version shortly after create.
- Provider delta reads never resend an unchanged copy.

The base is the deployed tag `v0.2.17`
(`5433784b7a9edf242d17b53fb4bd334af90df7c5`). This branch adds one code change
plus this version bump and these release documents.

The change refreshes a non-origin copy's validator after provider-only
changes. It works in two parts.

**Pull path.** A non-origin observation refreshes only the copy's stored
version and provider-state baseline, and only when every guard holds:

- The copy was created by Musubi for the same account owner, proven by a
  completed create outbox row and the same creator.
- No local write is pending.
- There is no redaction or privacy recovery.
- The event is non-recurring, with legacy time.
- The provider grants full read access.
- The serialized content is identical.
- The copy has no attendees or conference and is an active single instance.
- The provider itself proves the organizer is the owner. Graph uses
  `isOrganizer`, Google uses `organizer.self`, and CalDAV has no ORGANIZER.
- The baseline is unchanged, or, when there is no baseline, privacy is the
  provider default.

Shared content, revision, `updatedAt`, delta and fanout never change. A skip
logs only the first failing guard name and the names of differing baseline
fields.

**Request path.** When a strict write preflight reports `provider-conflict`,
every non-origin provider copy of the operation is re-read once, read-only,
under one shared delivery deadline of 45 s. Each read goes through the same
guarded ingestion. A copy missing from that read is skipped, with no database
call and no unlink. The original 409 with `localCommitted: false` is always
returned, and nothing is retried automatically. The user's next attempt runs
the unchanged strict preflight.

The CalDAV single-event read now carries provider state, as the pull path
already did.

User-visible changes are in [0.2.18-notes.md](0.2.18-notes.md). The release
job uses that file as the GitHub release body. GitHub also appends its
generated notes after it.

## Verified against `v0.2.17`

Checked with `git diff v0.2.17..HEAD` on this branch:

- **Database.** There are no changes under `packages/db/drizzle`, to
  `packages/db/src/schema.ts` or to `apps/client`. The migration journal still
  has 88 entries, `0000` through `0087_project_news`. The refresh writes only
  existing columns: `external_events.etag`, `provider_state`,
  `provider_state_observed_at` and `ical_uid`.
- **Deployment and configuration.** There are no changes to `.github/`, any
  Dockerfile, `apps/web` or the environment variables production code reads.
  The only new `process.env` line is a test guard.
- **Types and protocol.** `packages/types` changes only `PRODUCT_VERSION`, so
  `MIN_CLIENT_VERSION` and `MIN_PEER_VERSION` stay `0.2.0`. The event-write
  response shapes, the task schemas and the task mutation protocol are
  unchanged.
- **Stored CalDAV snapshot.** CalDAV delete delivery stores
  `remote_snapshot.values` as JSON. That snapshot now also contains a
  `providerState` key, which is already the Microsoft shape. The column type is
  an open record, and the only reader is a non-strict field pick. 0.2.17 reads
  such rows unchanged.

This branch changes the root `package.json` version and
`packages/types/src/version.ts` `PRODUCT_VERSION` (0.2.17 → 0.2.18).
Workspace packages and `apps/client/app.config.ts` inherit the root version.
No mobile EAS build, submission or distribution is in scope. CI Android
validation still builds APK/AAB artifacts that report 0.2.18, but nothing
distributes them.

## Known limits

- **Shared events.** Copies of events created by another member stay
  fail-closed and can still stay blocked.
- **Recurring events, meetings and time editing.** These are out of scope.
  This covers recurring events, events with guests or conferences, and the
  `EVENT_TIME_EDITS_ENABLED=true` path. With that flag on, Google copies fail
  closed. Separately, CalDAV collection reads already throw for non-origin
  components. That is a pre-existing issue to fix before enabling the flag for
  users with mixed calendars.
- **Real provider-side changes still block.**
  - Outlook body normalization of multi-line descriptions is unproven. It
    fails closed.
  - A changed baseline field fails closed.
  - So does a CalDAV ORGANIZER added by the server. The skip log names the
    guard.
- **The origin copy's post-create race remains.** It conflicts until the next
  origin pull.
- **Worker-side delivery conflicts are not covered.** They use the existing
  resolution flow, and this change does not assess it.
- **Lock waits on the 409 path.** The request-path refresh waits on the same
  calendar and event locks that the successful path already takes. There is no
  separate lock timeout.

## Rollback

0.2.18 adds no migration and no new storage semantics relative to `v0.2.17`.
It only refreshes existing mapping columns, so an image-only rollback to the
previously verified 0.2.17 immutable images is schema-compatible, with no
database restore. Confirm those indexes against the runtime observed before
deployment.

- Keep the runbook's stop-first, single-API discipline: stop the 0.2.18 API
  before starting the old one.
- Do not restore the database automatically. A restore would discard real
  writes made after the backup, and it cannot undo changes already delivered
  to providers.
- Validators refreshed by 0.2.18 stay stored after a rollback. Each one was
  verified against the live provider copy, and 0.2.17's strict preflight still
  compares it with the live version on every write.
- A rollback brings back the permanent `provider-conflict` for affected
  copies. Prefer a reviewed forward fix.
- Do not clear cursors, queues or etags. Do not weaken guards, rewrite
  migration history or replay uncertain writes.
