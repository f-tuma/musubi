# Musubi 0.2.5 release notes

This API/web hotfix extends Microsoft calendar delta continuation validation
to authenticated canonical calendar resources. Version 0.2.4 corrected a
reproduced ID-encoding defect. Live verification still rejected Graph
continuations because their resource prefix differed from the requested
`/me/calendars/{id}` form.

When a continuation uses a recognized canonical resource form, the reader
first fetches the constructed `/me/calendars/{bound-calendar-id}` endpoint
with the same token. It requires a complete, nonredirected 200 response, the
exact bound calendar ID and a valid absolute `@odata.id` whose explicit
calendar key also matches. A continuation must match the proven resource
path, or use the equivalent unnamed OData primary-key syntax within the
same token's `/me/calendars` collection, before it can be followed or
committed. Foreign `/users` paths require the exact proven owner and key
syntax; OAuth subject claims are never used to guess that identity.
The proof is fresh for each
reader invocation, including saved cursors, and is reused only within that
invocation. Ordinary continuations do not require this additional GET.

The provider's original continuation and opaque query bytes remain intact.
Different owners or calendar IDs, unknown aliases, default-calendar paths,
unsafe origins, credentials, fragments, parser-repaired paths and malformed
keys remain rejected. Failed identity proof cannot accept a partial page,
advance a cursor or authorize deletions. Fixed diagnostic fields contain no
URLs, tokens, owner/calendar IDs or response content.

Regression coverage exercises canonical REST/OData resource forms, key
encoding, saved cursors, proof freshness and caching, malformed or incomplete
proof responses, rejected pagination, 410 recovery, cycles and privacy.
Actual post-rollout Microsoft pulls remain the acceptance gate; publication
or a healthy API alone does not establish recovery.

## Upgrade and remaining limits

There is **no new database migration relative to 0.2.3 or 0.2.4**. The existing
journal still ends at `0085_graph_read_coverage`. Client and peer minimums
remain 0.2.0. Existing provider gates, encoder, recovery configuration and
Vardum asset URLs are unchanged. This release does not upload artwork or
publish native store builds.

Use the [0.2.3 deployment and recovery procedure](https://github.com/f-tuma/musubi/blob/main/docs/releases/0.2.3-deployment.md)
with the same singleton, consumer, backup and recovery boundaries. Publish
with `version=0.2.5` and the full reviewed `expected_source_sha`; the fresh tag
can automatically deploy API and web. Record source, green checks, immutable
images and actual runtime observations separately. Reconcile an uncertain
publication result before another attempt; never force or recreate a tag.

Mailbox-unavailable 404s, missing skip-token 400s, CalDAV discovery/fallback
warnings and long scheduler sweeps have separate investigations. No new
provider permissions, C07 features or delivery replay are included.
