# Musubi 0.2.2 deployment and recovery

This is the operator procedure for upgrading and recovering a 0.2.2 installation.
The accepted release revision is `aea392d0f6bf343794ff7eb6c056cf7d7d645690`;
[release status](https://musubi.pro/docs/operations/releases/) records published
digests, deployment observations and checks still open. The earlier candidate
review used `d034723`; that historical identifier is not the deployed-image proof.
This procedure itself does not certify a production backup or authorize an
unattended upgrade.

## Release boundary

The published `v0.2.1` tag contains PostgreSQL migrations through 0078. The
candidate adds:

| Migration | Change |
| --- | --- |
| 0079 | Outlook occurrence move journal and leases |
| 0080 | Canonical task home, memberships, revisions, mutation ledger and delivery outbox; source-scoped mapping backfill |
| 0081 | Task projection source lookup index |
| 0082 | Actor-scoped fork request fingerprint |
| 0083 | Durable fork commit/noncommit outcome |
| 0084 | User-facing 0.2.2 release announcement |

0080 preserves task UUIDs, provider IDs, validators, tombstones and SEQUENCE.
It backfills the previous calendar as home and creates one membership per task.
It also makes `calendar_id` nullable and changes its calendar foreign key from
cascading deletion to `SET NULL`. There is no down migration. The actual
production migration journal must be recorded; `/api/v1/server` reporting a
product version does not identify its image revision or migration state.

The API acquires its PostgreSQL singleton lock before applying migrations and
before listening. Run exactly one API replica and stop the previous API before
starting its replacement. A start-first rolling update cannot overlap two API
processes against the same database.

Released native clients keep compatible reads and other application features,
but their legacy task writes receive 426 before saving. A client built from the
0.2.2 revision is required for task creation, editing, completion, deletion and
sharing. See [mobile rollout](0.2.2-mobile.md). Deploying the API before that
build is available accepts a temporary loss of native task writes; there is no
safe legacy-write fallback.

## Configuration and remaining evidence

Preserve each existing production Core gate. Do not copy the historical
[Core activation example](core-0.2.0-activation.md) into production as part of
this upgrade. In particular, do not newly enable iCloud RSVP, provider reminders,
CalDAV alarms or Google availability. This release does not provide new live
acceptance for those paths.

Shared task writes have no rollout flag. They become available with the new
API and clients. `EXTERNAL_SYNC_INTERVAL_MIN=0` disables scheduled sync and
outbox draining, but task mutation handlers still wake provider delivery after
commit; it is not a task-write kill switch. Blocking public API access and
stopping the API is the recovery boundary.

The automated candidate checks cover migration preservation, task ownership,
revision/privacy admission, API compatibility, durable delivery and fork replay,
plus unit, browser and Storybook behavior. Live provider acceptance, physical
native acceptance and the production image/migration/backup inventory remain
separate evidence. A decision to proceed before them is an explicit acceptance
of that release risk, not proof they passed.

## Prepare publication and maintenance

The manual `Publish Docker images` workflow runs from `main`, verifies the
requested version and runs Quality. It builds API and web for AMD64 and ARM64,
publishes both manifests, then creates `v0.2.2` and its GitHub release. The tag
is the intended Dokploy deployment signal. Do not create a deployment tag by
hand before its images exist.

Before dispatching that workflow, inspect the real Dokploy trigger and pause
automatic deployment if necessary until the backup and maintenance window are
ready. Pin production to the accepted version or image digests; do not use
`latest` as the recovery reference. API and web must come from the same final
release revision. Keep the previous API/web digests and deployment configuration.

## Upgrade

1. Record the running API/web digests and revisions, migration journal, Core
   gates and current task, calendar and provider-mapping counts. Record
   unresolved event/task deliveries and running Outlook move journals when
   those tables exist. Keep secrets and private task text out of this record.
2. Hold public API access in maintenance and stop the old API, including its
   background workers. Create a custom PostgreSQL dump and preserve local media
   when `S3_BUCKET` is unset. Protect remote media through its existing backup
   policy. Retain the required encryption keys and old configuration separately
   from the release record.
3. Restore the dump into isolated PostgreSQL before upgrading. The repository
   helpers use the Compose `db` service; when the production checkout uses the
   Dokploy Compose file, pass its absolute path as `MUSUBI_COMPOSE_FILE` to
   `./ops/backup-postgres.sh`. Verify the resulting custom dump with
   `./ops/verify-postgres-backup.sh /absolute/path/to/backup.dump`. A successful
   helper run proves restore completion and nonempty public tables; also compare
   task/calendar/mapping counts and migration journal against the source record.
4. Start one API replica using the accepted 0.2.2 image, retaining the current
   production settings. Its boot migrator applies the pending journal before
   HTTP starts. Verify the API image revision/digest, migration completion,
   `/api/v1/server/ok`, advertised 0.2.2 version and an authenticated calendar
   and task read before releasing public traffic. Compare task UUID/home and
   membership preservation with the backup, including tombstones.
5. Start the matching web artifact. Run a local task create/change/complete/read
   smoke check with a designated test account. Retain those test operations in
   the release record. Publish the native store build once its acceptance and
   distribution are ready. If API/web are deliberately released first, record
   the temporary native task-write gap and direct those users to web. Keep the
   legacy task rejection routes and current revision/privacy requirements.
6. Reopen public access only after the maintenance checks pass. Inspect account
   sync failures, source discovery and task delivery state during initial
   traffic. A committed local task does not prove all provider destinations
   received it. Keep unsupported Microsoft live links blocked; independent
   copies retain their own home.

These read-only queries record counts without task content:

```sql
SELECT count(*) AS tasks,
       count(*) FILTER (WHERE deleted_at IS NOT NULL) AS tombstones
FROM tasks;
SELECT count(*) AS calendars FROM calendars;
SELECT count(*) AS provider_task_mappings FROM external_tasks;
SELECT id, created_at, hash
FROM drizzle.__drizzle_migrations ORDER BY created_at;
```

After migrating from the pre-0080 database, home/membership preservation can be
checked before any calendar lifecycle changes. Investigate a nonzero result;
do not repair it by rewriting the migration journal:

```sql
SELECT count(*) AS missing_home_memberships
FROM tasks t
WHERE t.calendar_id IS NOT NULL
  AND (t.origin_calendar_id IS DISTINCT FROM t.calendar_id OR NOT EXISTS (
    SELECT 1 FROM calendar_tasks ct
    WHERE ct.task_id = t.id AND ct.calendar_id = t.calendar_id
  ));
```

The existing event-outbox gauges do not monitor task delivery backlog. Use the
sanitized task delivery UI and aggregate queue state as well as Grafana's
account/push failures. Queue counters after smoke checks and initial traffic:

```sql
SELECT provider, status, error_code, uncertain, count(*) AS operations,
       min(created_at) AS oldest_created_at
FROM task_outbox
WHERE status NOT IN ('completed', 'not-needed', 'cancelled')
GROUP BY provider, status, error_code, uncertain;
```

## Recovery

An image-only downgrade to the old API is unsafe after 0080, even if users have
not created a shared task yet. Old creates and provider imports omit
`calendar_tasks` and `origin_calendar_id`. Old updates bypass task revision CAS
and outbox fanout; old provider deletions ignore shared memberships. The old
migrator does not rerun the recorded backfill.

If the new release must be withdrawn:

1. Stop the API and keep public writes blocked. Save an incident dump before
   restoring anything. It retains canonical updates, mutations, task outbox
   addresses and uncertain results, plus Outlook move journals needed to assess
   remote effects.
2. Prefer a compatible forward fix when accepted writes must be retained.
   Otherwise restore the verified preupgrade dump into a clean database and
   start the exact prior API/web digests with their preserved configuration and
   encryption keys. Restore local media consistently if it changed.
3. Verify the old migration journal, login and authenticated calendar/task reads
   before reopening traffic. Review operations accepted during the upgrade
   window. Restoring PostgreSQL does not undo provider invitations or Google,
   Microsoft and CalDAV task changes already delivered. Reconcile those effects
   from the incident evidence; never blindly repeat uncertain CREATE operations.

Do not manually drop task tables/columns, rewrite migration history, delete
receipts, or run the old task writer against the upgraded database.
