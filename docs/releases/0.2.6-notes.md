# Musubi 0.2.6 release notes

This API/web hotfix removes the mandatory dependency on optional calendar
`@odata.id` metadata when independently proving Microsoft delta routes.
Live verification of 0.2.5 reached a complete calendar GET with the expected
native ID, then failed canonical-resource validation. The logs do not establish
whether the annotation was absent or had an unsupported form.

A fresh, complete, nonredirected GET of the constructed bound-calendar endpoint
now proves the same token's explicit `/me/calendars` primary-key routes. For a
`/users` continuation without an exact canonical binding, the reader also GETs
the constructed `/me?$select=id` endpoint and requires its returned opaque Graph
user ID to match the candidate owner exactly after one key decode. Both proofs
are local to one invocation and repeated for saved canonical cursors.

An exact authenticated canonical resource remains usable when provided.
Unusable optional metadata contributes no authority to the independent proof
rules and is never fetched. A recognized Graph annotation explicitly naming a
different calendar ID is contradictory and still fails the read. Composite
owner keys, email/UPN spellings and OAuth subjects are never guessed from a
bare profile ID. An owner without either proof remains rejected.

All continuation origin, protocol, API version, raw-path and explicit calendar
key checks remain enforced before any proof. Provider URL/query bytes, window
bounds and independent deletion authority are preserved. Unavailable identity
proof cannot accept a partial page or advance a cursor. Diagnostics retain
fixed candidate/metadata classifications and evaluated-match booleans, never
URLs, IDs, tokens or response content. The existing Microsoft provider already
requests `User.Read`; this release adds no requested OAuth scope.

## Upgrade and remaining limits

There is **no new database migration relative to 0.2.3–0.2.5**. The existing
journal still ends at `0085_graph_read_coverage`; client and peer minimums stay
at 0.2.0. Provider gates, encoder/recovery configuration, Vardum URLs, artwork,
marketing and native store distribution are unchanged.

Use the [0.2.3 deployment and recovery procedure](https://github.com/f-tuma/musubi/blob/main/docs/releases/0.2.3-deployment.md).
Publish with `version=0.2.6` and the full reviewed `expected_source_sha`; a fresh
tag can automatically deploy API and web. Source review, green CI, immutable
images and actual running observations remain separate evidence. Reconcile an
uncertain publication result before another attempt; never recreate a tag.

Actual post-rollout Microsoft pulls remain the acceptance gate. Neither
0.2.4 nor 0.2.5 resolved the live incident. Mailbox-unavailable 404s, skip-token
400s, CalDAV warnings and scheduler fairness retain separate investigations.
