# Musubi 0.2.12

## Sync delivery and scheduling

- Shared, versioned delivery code now covers the accepted event, task, reminder,
  RSVP and scheduling families for Google, Microsoft and CalDAV. Existing
  provider capabilities, gates, native validators and completion policies remain
  separate; internal extraction does not enable previously deferred operations.
- Durable provider cooldowns and fair work scheduling retain retry timing across
  restarts and prevent a busy connection from monopolizing work. Progressing
  pagination keeps its stall watchdog without a fixed aggregate read deadline.
- The standalone sync candidate has an installed conformance corpus and an
  independent reference host. Its packaging and verification do not publish a
  public package or establish real-provider acceptance.

## News and updates

- Servers read common project news from the repository's validated `news.json`.
  The web and mobile readers use a separate read marker and baseline historical
  items on their first successful read.
- Per-server announcement administration and SQL content storage are removed.
  A temporarily unavailable source does not mark news read. Publishing news
  content remains separate from publishing or deploying this release.

## Release hardening

- The web logo has intrinsic dimensions, preventing an oversized flash while
  styles are loading during the first page render.
- Updated the API request parser, web framework, validation, mail, HTTP and
  related build dependencies. The production Node base is pinned to the vendor's
  22.23.4 security release. Bounded regression checks exercise the real parser
  and preserve previously promised wire formats.
- Android website association has a public endpoint configured with
  `ANDROID_APP_LINKS_SHA256`. Operators must supply the actual Play app-signing
  certificate fingerprints; an unset value publishes no association. Install
  and verify the Play-distributed app before claiming verified App Links.
- Notification-worker responses explicitly disable origin/CDN caching and
  registration bypasses the browser HTTP cache. External cache rules still need
  their own verification at the served origin.
- Backup verification cleans up only its own created container ID, uses an
  isolated temporary database and can compare supplied preservation SQL with a
  stopped-source baseline. A real production restore remains a separate check.

## Upgrade and distribution

The source migration journal has **88 entries through 0087**. Relative to the
published 0.2.11 source, 0086 adds durable scheduling state and 0087 removes the
old announcements table. Inspect the actual running journal before upgrading.
Stop all old API/consumer processes before starting one new API. Startup can
dispatch accepted work before HTTP is listening.

Take and verify the stopped-writer database/media/configuration backup first.
An old 0.2.11 API cannot run against the contracted 0087 schema. Recovery needs
a compatible forward fix or matching old artifacts and restored state, followed
by reconciliation of provider effects; never blindly replay uncertain creates.

Global client and peer minimums remain **0.2.0**. Task writes still require the
mutation protocol introduced in **0.2.2**; older task writers receive 426 while
compatible reads remain available. Existing Core activation decisions stay in
force, including deferred iCloud attendee RSVP.

Follow [the operator runbook](0.2.12-readiness.md): API first, matching web next,
then tested mobile distribution. Signed Android/iOS builds, store processing,
device acceptance and rollout status need their own evidence. There is no OTA
channel; halting rollout does not revert phones already updated.

These notes describe the versioned source. Artifact publication, production
deployment and mobile availability are separate checkpoints.
