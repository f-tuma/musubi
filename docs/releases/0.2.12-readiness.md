### Dependency security evidence

The official npm Bulk Advisory endpoint returned HTTP 200 for the unchanged
lockfile on 27 October. The all-lock inventory matched **83 advisory records**
(7 critical, 30 high, 33 moderate, 13 low), including development/build tooling
and several packages for one advisory. These are **not unique vulnerabilities
or proven exploitable production paths**. Conservative dependency closures also
expand optional peers, so their membership alone is not runtime proof. The
[filtered security receipt](evidence/2026-10-27-security.json) records this scope.

- **Confirmed source precondition:** `express.json({limit:"512kb"})` in
  `apps/api/src/index.ts` uses `body-parser@2.3.0` before authentication and leaves
  decompression enabled. [GHSA-27r3-jxmh-p828](https://github.com/advisories/GHSA-27r3-jxmh-p828)
  is fixed in 2.4.0; the vendor also documents `inflate:false` when compressed
  bodies are unnecessary. No crash/exploit request was sent to production.
- **Web framework:** `@tanstack/react-start@1.168.32` and
  `@tanstack/start-server-core@1.169.17` match a
  [critical reflected-XSS advisory](https://github.com/advisories/GHSA-qx66-fv34-fjm8),
  fixed in 1.168.60 / 1.169.39. The framework and gateway server-function path
  are present, but no app server-function declarations were found and the local
  generated manifest was empty. Execution is unproven for the final deployed
  artifact; require a fixed build or explicit version-bound non-reachability
  evidence before GO.
- **Conditional/configuration-dependent matches:** `proxy-addr@2.0.7` matches a
  [critical advisory](https://github.com/advisories/GHSA-jqcg-44mw-7w3h), fixed in
  2.0.8; the dangerous trust-subnet configuration was not observed. Nodemailer,
  undici and Zod matches need their input/API paths reviewed. npm undici and
  Node's bundled fetch implementation are distinct audit targets.

No dependency changes were made. Built API/web images, base-OS/Node dependencies
and signed mobile binaries were not scanned; green Quality is not a clean
security attestation. Keep dev/preview servers restricted while reviewing their
separate advisory matches.

## C. Record production baseline and prove recovery

Before any publication/deployment action, an operator records:

- API/web deployment/container IDs, Created/StartedAt and actual immutable image
  digests/OCI source revisions; all API, worker and custom consumers, including
  consumers outside the supplied singleton process.
- Exact daemon/context, Compose file **and Compose project name**. A path alone
  is insufficient for Dokploy; do not accidentally address a second stack.
- Effective configuration through an explicit whitelist, including UNSET/default
  versus configured values: Core gates, encoder, recovery/polling, stable budget
  namespace, auth/public origin, media and OAuth/callback settings. Preserve
  secrets/encryption keys privately; do not dump `env` into the release record.
- Ordered production Drizzle journal and content-free preservation/queue counts,
  oldest/due/uncertain work, last complete pulls and active provider cooldowns.
  Do not export identities, event bodies, tokens or accepted payloads publicly.
- Actual tag-trigger controls, stop-first/API→web order, maintenance window,
  previous compatible recovery artifacts and the person responsible for the
  switch. Hold any mutable-`latest` polling as well as tag-triggered automation.

The published 0.2.11 source journal ends at 0085; the candidate has **88 entries
through 0087**. Actual pending migrations come from the runtime journal, not the
public product version. 0086 adds durable scheduling/cooldown state; 0087 drops
`announcements` and adds the separate news marker. For read-only inspection use
bounded transactions, for example:

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '10s';
SET LOCAL TIME ZONE 'UTC';
SET LOCAL DateStyle = 'ISO, YMD';
SELECT id, created_at, hash FROM drizzle.__drizzle_migrations ORDER BY id;
SELECT count(*) AS tasks,
       count(*) FILTER (WHERE deleted_at IS NOT NULL) AS task_tombstones FROM tasks;
SELECT count(*) AS calendars FROM calendars;
SELECT count(*) AS memberships FROM calendar_tasks;
SELECT count(*) AS task_mappings FROM external_tasks;
SELECT provider, status, uncertain, count(*) AS operations, min(created_at) AS oldest
FROM task_outbox GROUP BY provider, status, uncertain ORDER BY provider, status, uncertain;
SELECT provider, status, uncertain, count(*) AS operations, min(created_at) AS oldest
FROM event_outbox GROUP BY provider, status, uncertain ORDER BY provider, status, uncertain;
SELECT status, count(*) AS moves, min(created_at) AS oldest FROM outlook_moves GROUP BY status ORDER BY status;
SELECT to_regclass('public.sync_read_work'), to_regclass('public.provider_budget_cooldowns');
COMMIT;
```

Use the existing [preservation checks](0.2.2-deployment.md) and inspect the
0086-only tables only when present. Compare counts and journal on restore and
after migration, accounting for deliberately removed announcement content and
expected new scheduling rows. A successful backup command alone is not a restore
test.

Enter maintenance, block public writes, stop **all old API/consumer processes**,
then create the consistent backup. Keep one API replica for the later startup.
For a fresh private release evidence directory, the existing dump helper is:

```sh
# Set these to the EXISTING deployment identity and a fresh private backup folder.
set -eu
export COMPOSE_PROJECT_NAME="${MUSUBI_EXISTING_COMPOSE_PROJECT:?Set the existing project}"
export MUSUBI_COMPOSE_FILE="${MUSUBI_EXISTING_COMPOSE_FILE:?Set the existing Compose file}"
export MUSUBI_BACKUP_DIR="${MUSUBI_RELEASE_BACKUP_DIRECTORY:?Set a fresh private release directory}"
# Save the reviewed read-only SQL above as MUSUBI_RELEASE_COUNTS_SQL.
# Re-capture the baseline AFTER every writer/consumer has stopped.
: "${MUSUBI_RELEASE_COUNTS_SQL:?Set the reviewed preservation SQL file}"
test -r "$MUSUBI_RELEASE_COUNTS_SQL"
umask 077
mkdir -p "$MUSUBI_BACKUP_DIR"
docker compose -f "$MUSUBI_COMPOSE_FILE" exec -T db sh -ceu \
  'exec psql -X -v ON_ERROR_STOP=1 -P pager=off -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < "$MUSUBI_RELEASE_COUNTS_SQL" > "$MUSUBI_BACKUP_DIR/source-counts.txt"
./ops/backup-postgres.sh
```

Then set/export `MUSUBI_RELEASE_DUMP` to the actual new `.dump` reported by the
helper, not a guessed file name or a previous dump. Only then record its checksum:

```sh
: "${MUSUBI_RELEASE_DUMP:?Set the actual new dump path reported above}"
test -r "$MUSUBI_RELEASE_DUMP" && test -s "$MUSUBI_RELEASE_DUMP"
sha256sum "$MUSUBI_RELEASE_DUMP"
```

The helper has retention deletion inside its backup directory; do not point it
at unrelated/previous backup collections. Preserve local media when S3 is unset
and existing remote-media/key/config restore references otherwise.

Until the restore helper's ownership finding is fixed, use a deliberately owned
isolated restore. The following is an operator reference, **not executed by this
audit**. Use an approved immutable PostgreSQL image compatible with the dump.
Run this block as its own script so its exit trap closes only the owned restore:

```sh
set -eu
umask 077
: "${MUSUBI_RESTORE_IMAGE:?Set the approved PostgreSQL image digest}"
: "${MUSUBI_RELEASE_DUMP:?Set the actual readable custom-format dump}"
: "${MUSUBI_RELEASE_COUNTS_SQL:?Set the same preservation SQL file}"
: "${MUSUBI_BACKUP_DIR:?Set the private release evidence directory}"
case "$MUSUBI_RESTORE_IMAGE" in *@sha256:*) ;; *) exit 1 ;; esac
test -r "$MUSUBI_RELEASE_DUMP" && test -s "$MUSUBI_RELEASE_DUMP"
test -r "$MUSUBI_RELEASE_COUNTS_SQL"
test -r "$MUSUBI_BACKUP_DIR/source-counts.txt"
musubi_restore_nonce=$(python3 -c 'import uuid; print(uuid.uuid4().hex)')
musubi_restore_id=$(docker create --network none \
  --name "musubi-release-restore-$musubi_restore_nonce" \
  --label "musubi.release.restore=$musubi_restore_nonce" \
  --tmpfs /var/lib/postgresql/data \
  --env PGDATA=/var/lib/postgresql/data \
  --env POSTGRES_HOST_AUTH_METHOD=trust --env POSTGRES_DB=restore_check \
  "$MUSUBI_RESTORE_IMAGE")
# Install cleanup only AFTER successful creation; act on that returned ID only.
musubi_restore_cleanup() {
  docker stop -t 20 "$musubi_restore_id"
  docker rm "$musubi_restore_id"
}
trap musubi_restore_cleanup EXIT
docker start "$musubi_restore_id"
musubi_restore_attempt=0
# TCP stays unavailable during the official image's temporary init server.
until docker exec "$musubi_restore_id" pg_isready -h 127.0.0.1 -U postgres -d restore_check; do
  musubi_restore_attempt=$((musubi_restore_attempt + 1))
  test "$musubi_restore_attempt" -lt 30
  sleep 1
done
docker exec -i "$musubi_restore_id" pg_restore --exit-on-error --no-owner --no-acl \
  -U postgres -d restore_check < "$MUSUBI_RELEASE_DUMP"
docker exec -i "$musubi_restore_id" psql -X -v ON_ERROR_STOP=1 -P pager=off \
  -U postgres -d restore_check < "$MUSUBI_RELEASE_COUNTS_SQL" \
  > "$MUSUBI_BACKUP_DIR/restored-counts.txt"
diff -u "$MUSUBI_BACKUP_DIR/source-counts.txt" "$MUSUBI_BACKUP_DIR/restored-counts.txt"
```

There is no published port/network or production mount. No name-based forced
removal, global prune, forced database drop or session termination is used.
If creation fails, no cleanup trap runs. If cleanup cannot be confirmed, retain
the exact ID and inspect it; do not expand the cleanup target.

Release public mobile distribution **after the compatible API and web**. Begin
with internal/TestFlight acceptance and a small explicit Play staged rollout;
advance only on observed health. Public App Store version updates can use
Apple's seven-day phased release, but users may manually download immediately.
The TestFlight branch remains a beta channel unless the public-store conditions
are completed. Upload, review approval, rollout start and general availability
are four different statuses: record each accurately.

## Recovery and completion

Stop/pause mobile rollout and stop API/consumers/public writes on a serious
regression. Preserve an incident dump, actual journal, queues, accepted intents,
receipts and remote-effect evidence. Prefer a compatible forward fix when new
writes must survive. **Do not run the 0.2.11 API against the post-0087 schema.**
Restoring a matching pre-upgrade DB/media/config and exact prior artifacts is
the alternative; a database restore does not undo provider effects. Reconcile
uncertain/delivered operations and never blindly replay CREATEs. Never rewrite
migration history or delete accepted payloads/receipts to make recovery pass.

Halting a store rollout does not revert phones already updated. There is no OTA
channel here; deliver a new higher version/build and keep the server compatible.
Apple does not support reverting to an earlier App Store version. Recheck the
actual version floors before any recovery decision.

Close the release record only with the final source/proof IDs, API/web index
and running digests, journal/restore/maintenance evidence, accepted device and
store build IDs, live checks and rollout/monitoring decisions. Historical open
acceptance is closed by its own evidence, not by a green tag or merge.
