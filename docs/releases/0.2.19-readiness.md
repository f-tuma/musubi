## Scope

This is an API/web maintenance release for an iCloud write found during the
0.2.18 live provider check. A title edit of an event copied to an iCloud
calendar returned `403 {capability: "event-write", reason: "unknown"}` before
any local commit.

iCloud event resources answer `DAV:current-user-privilege-set` with an empty
`404` propstat. The legacy event PATCH preflight required an affirmative
`write-content` grant, so it could never pass. An approved narrow fallback
already existed for the series path and its known-time one-off content scope,
but not for this legacy PATCH preflight. Those known-time routes are unchanged.

The base is the deployed tag `v0.2.18`
(`f10d62206c975b21004017a33508334f1d664d5f`). This branch adds one source
change, implementation head `f59180c4e6a68f95b77a70b04101b0bd87f12755` (tree
`fc5a6a0b20bf13d1202484858e05676b248993d5`), plus this version bump and these
release documents.

The change applies to legacy `PATCH /api/v1/events` content updates (title,
description, location) of timed one-off events without an explicit time model,
on a verified iCloud destination. It covers both origin iCloud events and
Musubi mirrors.

- **Gate.** The only gate is the existing `ICLOUD_PERSONAL_CONTENT_WRITES_ENABLED`,
  which defaults to false. `EVENT_TIME_EDITS_ENABLED` is not consulted.
- **Preflight.** It re-derives eligibility at handler and worker time and
  persists nothing. It then refuses on, in order:
  1. ownership and link;
  2. the link owner's role;
  3. a strict resource URL;
  4. the resource ACL, where only an explicit empty 404 propstat may defer to
     the write;
  5. a fresh writable collection grant, which is necessary and never
     sufficient;
  6. a complete GET with the accepted strong ETag and UID;
  7. the strict personal shape: no organizer, METHOD, attendees, recurrence,
     extra components or all-day DATE.
- **Delivery.** Every legacy update of an iCloud-class destination uses a
  strict URL, refuses redirects, sends an `If-Match` PUT and reads the event
  back completely. Only the readback's own strong ETag is adopted.
- **Unconfirmed writes.** A readback mismatch or failure after acceptance is a
  schedulable `unconfirmed` outcome. It is settled by read on a later attempt,
  never by a blind repeat. The delivery host never ACKs an iCloud-class
  reconciliation observation without a strong ETag; a missing account fails
  closed.
- **Unchanged.** Known-time, scope, series, alarm, RSVP, organizer, create,
  delete, Google, Microsoft and non-iCloud CalDAV paths.

The contract and its limits are in
[caldav-series-writes.md](../sync/caldav-series-writes.md#icloud-legacy-one-off-content-updates-2026-11-07).
User-visible changes are in [0.2.19-notes.md](0.2.19-notes.md). The release
job uses that file as the GitHub release body, and GitHub appends its generated
notes after it.

## Behaviour with the image alone

With the flag unset, every observed iCloud response is refused before commit,
exactly as in 0.2.18: one resource PROPFIND, then `403 event-write/unknown`, no
outbox row.

The stricter iCloud-class delivery and the strong-ETag reconciliation guard
are not flag-gated. With the flag off they are reachable only in two cases,
neither of which has been observed on iCloud:

- after an affirmative resource grant;
- for an `unconfirmed` row whose read returns a non-strong ETag.

Deploying 0.2.19 therefore does not activate the repair.

## Known limits

- **All-day, recurring and meeting events.** Legacy all-day iCloud one-offs,
  recurring events and events with guests or an organizer stay unsupported.
  All-day support is a separate future slice.
- **Unobserved live iCloud behaviour.** This covers:
  - read-only shared collections;
  - a PUT response ETag;
  - one-off readback byte stability;
  - a collection PROPFIND with `redirect: "error"`.

  If iCloud rewrites bytes, an edit first answers `502
  event-delivery-unconfirmed` with `localCommitted: true`. It then completes on
  the next due attempt by reconciliation.
- **Weak ETags.** A permanently weak or missing iCloud ETag, never observed,
  would keep a row `unconfirmed`, retried with backoff capped at one hour.
  Watch persistent iCloud `unconfirmed` / `provider-write-failed` rows in
  delivery status. No new metric is added.
- **Mixed providers.** With several providers, the documented first
  `409 provider-conflict` (for example Microsoft) and an explicit retry remain.
  Inline delivery stops at the first failing row, and later rows stay pending
  for the background worker. Read the final row states, not only the response.
- **Microsoft and Google undefined permissions.** Microsoft `canEdit` or Google
  `accessRole` becoming undefined is not strictly excluded as a cause of the
  original 403.

## Rollback

0.2.19 adds no migration and no new storage semantics relative to `v0.2.18`.
It writes only existing columns.

**Narrow rollback (preferred).** Unset `ICLOUD_PERSONAL_CONTENT_WRITES_ENABLED`
and redeploy.

- New legacy iCloud updates are refused with 403 before commit.
- Already committed `pending` or `retry` rows re-run preflight, become
  ineligible and settle as `blocked/provider-permission-unknown`. Local content
  then stays ahead of the iCloud copy until the user acts.
- `unconfirmed` rows reconcile by read first. A matching strong observation
  completes. Otherwise, with an unchanged validator the re-preflight blocks,
  and with a changed validator the row settles as a conflict.
- Completed rows remain.

**Image rollback.** Going back to the previously verified 0.2.18 immutable
images is schema-compatible, with no database restore. Confirm those indexes
against the runtime observed before deployment.

- Keep the runbook's stop-first, single-API discipline.
- With the flag unset, 0.2.18 handles any remaining rows with its strict
  preflight. Prefer unsetting the flag first, so committed rows settle under
  0.2.19's own rules.
- Do not restore the database automatically. A restore would discard real
  writes made after the backup, and it cannot undo changes already delivered
  to providers.
- Do not clear cursors, queues or ETags, weaken guards, rewrite migration
  history or replay uncertain writes.
