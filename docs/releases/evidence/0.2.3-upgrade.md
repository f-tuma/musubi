# 0.2.3 synthetic backup, restore and upgrade evidence

Recorded 13 October 2026. This verifies local mechanics only; production journal,
backup/restore acceptance and deployment remain UNKNOWN. No provider writes or
live database access occurred. All values and data were synthetic.

## Inputs and actual execution

- Exact old release: `v0.2.2`, commit `aea392d0f6bf343794ff7eb6c056cf7d7d645690`.
- Candidate runtime: `601836b4f3ecd78a2cd86acf6719e9c7127cac38`.
- PostgreSQL 17.11, `postgres:17-alpine`, owned loopback
  fixture `musubi-release-upgrade-1a9fef53fe6d` on port 55440.
- The tag's entire Drizzle folder and journal were extracted with `git archive`.
  All 85 old SQL/journal entries through 0084 byte-match the candidate prefix.
  The same runtime Drizzle node-postgres migrator installed that old schema.
- Seeded 28 rows across 14 nonempty public tables; the schema has 40 public
  tables. Live/deleted canonical data, memberships, mappings, an address
  tombstone and four opaque legacy outbox payloads were present before backup.
- Executed the repository backup helper against a synthetic Compose file and
  backup directory. Executed the repository restore helper against both its
  custom archive and gzip-compressed custom archive. Each restored 40 public
  tables and cleaned its own temporary container.
- Restored the identical archive into a separate fixture database with
  `pg_restore --exit-on-error --no-owner --no-acl`. All public rows and all
  old journal rows exactly matched the pre-backup snapshot.
- Ran actual candidate `packages/db/src/migrate.ts` twice. The first pass added
  exactly migration 0085; the journal moved 85→86. The second pass changed
  neither rows nor journal. Old columns, identifiers, payloads and statuses were
  compared field by field, not only by count.
- Ran the existing `source-read.integration.test.ts`: 11 scenarios passed.
  Its own fixture cleanup and the separate trigger proof's SQL ROLLBACK left
  the whole upgraded snapshot identical to both migration passes.

The local harness used nonce ownership labels and refused preexisting/unowned
containers. A Docker wrapper translated the restore helper's generated names
into nonce-owned names; helper source stayed unchanged. Containers and the owned
Compose network were removed. Dumps were private mode-600 files in a mode-700
local temporary directory. The harness and logs were retained locally under
`/tmp/musubi-release-upgrade-1a9fef53fe6d`; they contain synthetic data.

## Trigger and constraint proof

Routine usable access/refresh-token rotation retained generation 0. Scope ABA
advanced 0→1→2, status ABA 2→3→4, token revoke advanced to 5, null→empty stayed
5, and relink advanced to 6. Caller attempts to reset or jump the counter both
retained 6. ROLLBACK restored the original account generation 0. Each new
nonnegative constraint rejected invalid insertion with SQLSTATE 23514; exactly
one account generation trigger existed.

## Commands and supported archive format

The repository helpers were invoked with the owned synthetic paths:

```sh
MUSUBI_COMPOSE_FILE=/tmp/musubi-release-upgrade-1a9fef53fe6d/compose.yml \
MUSUBI_BACKUP_DIR=/tmp/musubi-release-upgrade-1a9fef53fe6d/backups \
MUSUBI_BACKUP_RETENTION_DAYS=14 sh ops/backup-postgres.sh

# PATH in the fixture pointed to the nonce ownership/name guard.
sh ops/verify-postgres-backup.sh /tmp/musubi-release-upgrade-1a9fef53fe6d/synthetic-v0.2.2-only.dump
sh ops/verify-postgres-backup.sh /tmp/musubi-release-upgrade-1a9fef53fe6d/synthetic-v0.2.2-custom.dump.gz

# Isolated fixture URL and test configuration were provided; no live DB.
pnpm --filter @musubi/db exec tsx src/migrate.ts
# Repeat the same migrator, comparing ordered public rows and journal each time.
pnpm --filter @musubi/db exec tsx src/queries/source-read.integration.test.ts
```

The restore helper advertises `.sql.gz`, but a genuine gzip-compressed text SQL
`pg_dump` failed with exit 1: pg_restore requires
an archive and directs text input to psql. Plain SQL is unsupported by this
helper. Custom archive and gzip(custom archive) passed. The release runbook's
produced `.dump` procedure is valid; no operations helper was changed.
