# Musubi 0.2.11 release notes

A valid CalDAV sync-collection REPORT with no changed resources now preserves
its root sync token. The convenience client previously dropped that metadata
when no resource response rows were present, causing an unnecessary complete
fallback read. The adapter now consumes the strictly validated token through
request-local metadata, independently of the resource-row count.

An incremental no-change result remains incremental: no reset, no fabricated
DAV resources and no replacement token from earlier discovery or another
request. Initial synchronization keeps its existing reset semantics. Concurrent
reads cannot exchange tokens. Metadata is bound to the exact requested and
effective collection URL; sync REPORT redirects are refused and may use the
existing fully validated fallback. Caller-provided fetch overrides cannot
supply unverified rows to this helper.

Missing, duplicate, malformed, wrong-namespace, partial and failed responses
still fail validation. Hydration failure does not return a cursor. Seeded
regressions exercise actual HTTP, the guarded client, adapter, sync engine and
PostgreSQL to verify cursor progress only on a valid read while retaining
canonical events/tasks, mappings, linked copies and pending delivery intents.

This is separate from the iCloud principal-alias discovery rejection. The
owner's deferred read-only account test remains necessary for that incident.
The observed no-token warnings support this investigation but do not prove the
live XML shape or recovery of every CalDAV account.

## Upgrade and acceptance

There is **no new database migration relative to 0.2.10**; the source journal
still ends at `0085_graph_read_coverage` (86 entries). Client and peer minimums
remain 0.2.0. OAuth scopes, provider gates, encoder/recovery configuration,
artwork and native store distribution are unchanged.

Use the [existing deployment and recovery procedure](0.2.3-deployment.md) with
`version=0.2.11` and the final reviewed full `expected_source_sha`. Keep source
review, green checks, immutable publication and actual running revisions as
separate evidence. Existing authorization to proceed with automatic backups
is not proof of runtime journal, backup/restore, maintenance or consumer
replacement; preserve the missing operational evidence explicitly.

After rollout, bound the no-token fallback trend to the new startup and observe
actual scheduled reads/checkpoints separately from adapter object reads. Do not
interpret missing logs, debug parsed-event counts or unrelated successful
accounts as universal recovery. Compare scheduler duration only as an observed
trend, without attributing every change to this fix. The Microsoft and iCloud
incidents retain their own acceptance and upstream availability requirements.
