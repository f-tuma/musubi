## Migration and recovery acceptance

The candidate adds `0085_graph_read_coverage` beyond the v0.2.2 source journal
ending at 0084. It adds source/checkpoint generations, coverage/fingerprint fields
and the account grant-generation trigger. Reference-host schema migrations are
separate and are not applied by Musubi API startup.

The encoder source default ON is already approved. New v1 admission still
requires the compatible decoder and pinned codec in every actual consumer.
`EXTERNAL_DELIVERY_RECOVERY_MODE=independent` runs recovery at startup and every
15 seconds even when polling is 0; request-triggered delivery remains active in
all modes. Preserve the operator's selected behavior explicitly. None of these
flags is a write kill switch or a rollback of accepted envelopes.

The [current synthetic restore/upgrade proof](evidence/0.2.3-upgrade.md)
restored exact v0.2.2 schema/data, advanced the journal 85→86 once, preserved
28 rows across 40 tables and four opaque legacy outbox payloads, and passed
11 source-read scenarios. Backup and restore helpers passed the produced custom
archive; the restore helper does not support plain SQL despite its historical
usage label. All fixture resources were removed.

Local fresh DB, process-crash and synthetic upgrade/restore tests establish
mechanics only. Production acceptance must compare the actual restored journal,
counts and outstanding operations, then run the singleton migration and
supported authenticated/provider smoke checks. An image-only return to 0.2.2
cannot be assumed safe: its writer predates the new decoder. A verified DB
restore does not undo effects already delivered to providers.
