# 0.2.12 candidate hardening

Follow-up to the [27 October readiness audit](0.2.12-readiness.md). The versioned
candidate is **0.2.12**; the last published release remains **0.2.11**. Candidate
preparation does not authorize publication, production migration or store rollout.
The complete release remains **HOLD** until its operational/device conditions
have evidence. See the [release notes](0.2.12-notes.md) for the full scope.

## Implemented source changes

- The API uses the fixed `body-parser@2.4.0` through its actual production JSON
  middleware. Its compression support and decoded 512 KiB limit remain intact.
  An isolated HTTP child reproduced the old unhandled decompression crash, then
  passed the same malformed input and a subsequent healthy connection after
  the update. No test request was sent to production.
- Updated the affected framework, validator, mail and HTTP dependencies, plus
  compatible transitive/build fixes. TanStack Start is 1.168.60 with server core
  1.169.39; Zod is 4.6.6; Nodemailer is 10.1.4. Vite and its peer contexts use
  one verified fixed version. No automatic/forced audit fix was used.
- All four Node Dockerfiles use **22.23.4**, pinned to the verified official
  multiarch digest. The previous digest contained 22.23.1. Registry bytes/configs
  establish both amd64/arm64 bindings; own network-none amd64 execution confirms
  the runtime and bundled dependency versions. This is separate from the final
  application image and the actual deployed image.
- The exact `node-forge@1.4.1` release-age exception is bounded to that version.
  The vendor's RSA verification fix was inspected and the installed package
  accepted canonical input while rejecting the extra nested element. The
  exception does not exempt the publisher or future releases from policy.
- Zod's changed nullable JSON Schema spelling is compared semantically only
  where pure type unions are equivalent. Constraints and literal values remain
  significant. Stable wire email/datetime primitives preserve the original
  accepted values, including minute-only timestamps. The immutable **0.2.0**
  baseline and client/peer floors remain unchanged; existing civil-time and
  occurrence refinements still apply.
- The Android association endpoint/configuration, worker origin/CDN headers and
  browser registration policy are implemented. See
  [domain links and worker acceptance](../testing/mobile-links-and-worker-cache.md).
  An unset signing fingerprint still returns 404; no certificate was invented.
- Restore verification now cleans up only its created full container ID, with
  isolated PGDATA/network, bounded commands and optional source/restore count
  comparison. See [operator inputs and limits](../../ops/README.md). Code/port
  tests do not establish an actual production backup or restore.

## Verification and remaining evidence

The fast inventory has **680 scenarios in 22 suites**. Parser cases exercise
real HTTP in owned subprocesses; restore cases replace only command ports; App
Links and worker cases exercise production functions. Their scopes are in
[behavior scenarios](../testing/behavior-scenarios.md). Final full checks,
running-app confirmation and immutable artifact checks must bind to the final
reviewed source, rather than borrowing the initial audit's green SHA.

The official npm advisory recheck reduced the original 83 all-lock records to
two version matches: Zod 3.25.76 beneath Expo CLI and KaTeX 0.16.47 beneath
documentation's Mermaid dependency. These are not blanket runtime-safety
attestations. Do not force Zod 3 consumers to major 4. Final artifact inventory
and scoped disposition remain necessary, as do OS and Node-bundled dependency
checks. The separate source peer closures deliberately overinclude tooling.

Still required before a complete GO:

- Actual Play app-signing fingerprint/provenance, configured public response and
  domain verification using the Play-distributed candidate. The effective public
  gateway must forward the new well-known path to the API.
- Effective public worker freshness after the actual origin/gateway and scoped
  external cache configuration are verified. Source headers alone do not prove
  Cloudflare behavior.
- Explicit application of the effective gateway configuration. API/web image
  publication does not install or reload `ops/gateway/Caddyfile`; record the
  operator's scoped gateway change separately.
- Dated production image/consumer/configuration/journal/queue inventory, the
  stopped-writer backup and compared isolated restore, and media/key/config
  recovery references.
- Exact signed Android/iOS artifacts, the selected iOS channel, store processing
  and the designated physical-device/provider acceptance matrix.
- Final reviewed source-bound CI, publication and deployment receipts kept as
  separate records. No tag or image pointer should be moved to make an incomplete
  record appear complete.
