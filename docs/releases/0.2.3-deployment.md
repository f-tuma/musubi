## Boundary and publication hold

The Musubi API journal ends at `0085_graph_read_coverage` (index 85, 86 entries
from `0000`). Relative to v0.2.2, this additive migration adds:

| Table | Change |
| --- | --- |
| `external_calendars` | Nonnegative `source_generation` and `checkpoint_revision`, each defaulting to zero; nullable `read_configuration_fingerprint` and `read_coverage` |
| `account` | Nonnegative `sync_read_generation`, defaulting to zero, and the `account_read_generation` trigger/function |

The account trigger advances generation for scope, sync status, refresh-token
presence or account identity changes, including loss→regain ABA. Routine
non-null token rotation does not advance it. The populated upgrade fixture
preserves historical identities, old columns and pending/unconfirmed payloads;
it is [local migration evidence](../planning/evidence/MUSU-34/populated-upgrade.md),
not a production backup or journal observation. The first new Graph read
replaces old cursors under coverage fences. No accepted payload backfill or new
announcement migration is included. The reference host's `schema-delete.sql`
applies to its own ledger, not the Musubi API database.

Record the running database's actual journal before deciding what boot will
apply; the committed journal does not establish production state. Installations
older than v0.2.2 must also follow the
[0.2.2 migration and recovery procedure](0.2.2-deployment.md).

Keep `MIN_CLIENT_VERSION` and `MIN_PEER_VERSION` at 0.2.0 and preserve the wire
baseline. Retain v0.2.2's task-specific legacy-write 426, revision/privacy
requirements, native distribution gap and outstanding provider/device evidence.
Do not interpret the root version read by Expo as a shipped phone build.
Preserve each existing production Core gate; historical activation examples do
not authorize new settings.

The `Publish Docker images` workflow runs from `refs/heads/main`, validates the
requested version and full approved `expected_source_sha`, reruns Quality and
publishes matching API/web manifests for AMD64 and ARM64. Every build/prepare/
release checkout is pinned to the captured source SHA. The guard rejects an
unapproved checkout and requires valid authenticated GitHub Not Found responses
for both the version tag and release; an outage, denied request or malformed
response is a stop, not absence. Paginated release-list checks reject visible
matching drafts, with the final check using the write-capable release-job token.

It updates both version tags and **`latest`**, repeats the guard, then pushes a
fresh non-force tag at the exact approved SHA and verifies its remote target.
The tag step emits its owned source SHA only after that proof. The create-only
release command requires the owned SHA and rechecks the exact remote target,
then sends one POST with the source release notes and generated notes enabled.
Only HTTP 201 is success; it never PATCHes/PUTs/deletes an existing release or
retries creation automatically. A hidden or concurrently created release is a
conflict requiring HOLD, not an update path. The operator confirmed on **14 October 2026** that a
new GitHub tag automatically deploys **both API and Musubi/apps/web**, while a
change to `latest` alone does not deploy. Treat tag creation as the deployment
boundary, even if the following release-body step fails. The
[workflow audit](0.2.3-workflow-audit.md) records fixes and remaining limits.

**Publication is held while automatic-deploy coordination, production
backup/restore proof and the maintenance decision are UNKNOWN.** The previous
running API/web digests and revisions, current database journal and actual
consumer inventory are also UNKNOWN until directly recorded. The workflow
cannot prove Dokploy's stop-first or API→web order. Do not dispatch publication
or create a release tag by hand while this hold remains. Follow
[release policy](../releasing.md) and preserve v0.2.2's historical evidence.

The workflow automatically uses `docs/releases/0.2.3-notes.md` as the GitHub
release body. Review that publication-ready source scope before dispatch.
Publication evidence establishes artifacts and a release, not a production
switch, live provider acceptance or phone distribution.

## Admission and recovery configuration

`SYNC_OPERATION_V1_ENCODER_ENABLED` has the already authorized source default
`true`. Unset and literal `true` admit new supported v1 operations; literal
`false` selects legacy admission for future operations. Other values fail boot.
Turning it off does not rewrite pending v1 rows, stop their dispatch or undo the
shared runner cutover. Existing v1 rows need the exact registered pinned codecs;
unknown or malformed formats remain HOLD before factories, credentials or HTTP.

Before production admission, verify the current decoder, pinned codecs and
connection-generation bridge in **every actual API process, delivery worker and
custom outbox consumer**. The supplied event/task consumers, request wakeups and
startup/15-second recovery share executors inside one API process. The singleton
lock protects that API, not the version of a custom external consumer. Stop all
old consumers and replace them before admission; do not use an overlapping
start-first rollout. Run exactly one API replica. Its lock is acquired before
migration and before listening. If consumer replacement is incomplete, explicit
`false` retains legacy admission until the current consumer inventory is proven;
it does not make an older worker safe for existing v1 rows. See the
[normative operation rollout contract](../protocol/sync-operation-v1.md).

| Configuration | Background behavior |
| --- | --- |
| `EXTERNAL_SYNC_INTERVAL_MIN=0` | Stops scheduled provider pull |
| `EXTERNAL_DELIVERY_RECOVERY_MODE=independent` (default) | Recovers event/task/move work at startup and every 15 seconds, including with polling at zero |
| `EXTERNAL_DELIVERY_RECOVERY_MODE=legacy` | Couples background recovery to a positive polling interval |
| `EXTERNAL_DELIVERY_RECOVERY_MODE=disabled` | Stops background recovery for any polling interval |

Request-triggered wakeups remain active in all modes. An installation that
used polling zero to pause recovery must select `legacy` explicitly to keep
that background behavior. Neither mode nor encoder settings are write kill
switches. Maintenance with public writes blocked and the API/consumers stopped
is the recovery boundary. The
[C01 delivery record](../planning/MUSU-32-delivery-recovery.md) describes finite
deadlines, Retry-After and content-free metrics.

1. Record the final reviewed release-control publication SHA and its green checks,
   separately from the frozen functional baseline. Inventory the running API,
   workers and custom consumers by environment, deployment identity, immutable
   image digest and source revision. Record previous API/web digests, actual
   migration journal, existing gates, encoder/recovery/poll settings and
   content-free task/calendar/provider-mapping counts. Also record unresolved
   event/task outboxes and Outlook move journals. Keep credentials, encryption
   keys and private content out of the release record; preserve required
   keys/configuration separately.
2. Coordinate the confirmed tag-driven deployment so it cannot start before
   maintenance is ready. Record the actual API→web and stop-first procedure;
   changing `latest` alone does not deploy. Hold public API access in maintenance
   and stop the old API and every consumer. Create a custom PostgreSQL dump with `./ops/backup-postgres.sh`;
   pass the absolute Dokploy Compose path as `MUSUBI_COMPOSE_FILE` when
   applicable. Preserve local media when `S3_BUCKET` is unset and follow the
   existing remote-media backup policy. Restore the dump in isolated PostgreSQL
   with `./ops/verify-postgres-backup.sh /absolute/path/to/backup.dump`. The
   helper accepts a custom archive (plain or gzip-compressed), not plain SQL,
   despite its historical `.sql.gz` usage label. Use the produced `.dump`. The
   helper proves restore completion and nonempty public tables; additionally
   compare the restored journal and counts with the source record. Record the
   approved maintenance window and restore proof before dispatch.
3. Dispatch `Publish Docker images` from `main`, with `version=0.2.3` and
   `expected_source_sha` set to the final approved full SHA, only after those
   operator inputs are recorded. The tag can start both deployments before the
   GitHub release body is complete. Record both immutable API/web index digests,
   architecture coverage and OCI revision labels from its actual results. Use matching
   artifacts from the accepted publication revision. Keep prior digests as
   recovery references; `latest` is not a recovery reference. If a tag push or
   release-body step fails, assume deployment may have started: inspect the exact
   tag, release, workflow and deployment state. Do not delete/recreate/force the
   tag or rerun the whole publication workflow automatically. Reconcile with the
   operator before resuming any step.
4. Start **one API replica**, with every old API/consumer stopped. Verify the
   actual digest/revision, singleton acquisition, migrator completion and
   expected journal through 0085. Record `server.started` including
   `syncOperationV1EncoderEnabled`, `syncOperationProfileVersion`,
   `externalSyncIntervalMin` and `externalDeliveryRecoveryMode`. Verify
   `/api/v1/server/ok`, advertised 0.2.3/minimum 0.2.0 and authenticated
   calendar/task reads. Confirm the current decoder/codecs for any replacement
   custom consumers before admitting new v1 work. Compare preserved counts,
   task home/memberships and tombstones before public traffic.
5. Start the matching web artifact. With an approved test account, verify login,
   calendar/event reads, task create/edit/complete/read, failure/draft behavior
   and delivery status. Check independent provider readback for the supported
   test operations; a local receipt alone is insufficient. Keep the first C07
   Google personal DELETE and C06 content UPDATE boundaries explicit. Record
   unresolved native distribution and physical-device checks, retaining the

6. Check the web branding on the live artifact: favicon, Apple icon, app-specific
   OG, both themes, a coloured calendar mark, original loading/offline fallback
   and notification worker icon/scope/click behavior. The stable `web-app`
   favicon, Apple icon and OG source URLs already have the intended keys;
   preserve their adopted original versions through the consumer rollout.
   Reopen public access only after maintenance checks pass, then observe
   sync/discovery failures, task/event queues, due lag and uncertain operations.
   The 0.2.2 runbook contains content-free SQL aggregates; compare them before
   and after smoke checks. Monitoring/live-provider acceptance remains separate
   from local source tests and publication.

## Recovery decision

Stop all API/consumer processes and block writes before recovery. Save an
incident dump and the actual journal, queue state, accepted envelopes and
provider-effect evidence. Prefer a compatible forward fix when accepted writes
need to be retained.

Migration 0085 is additive, but an older Graph reader can resume destructive
window sweeps. A binary rollback before the coverage fix is unsafe with active
Graph import. A worker older than the decoder floor is unsafe for a database
containing v1 envelopes; a decoder-only worker preserves them on HOLD but cannot
deliver without the exact pinned codecs. Explicit encoder `false` changes only
future admission and is not a dispatch rollback. Preserve accepted payloads,
receipts, ordering and uncertainty. The shared Google UPDATE/DELETE route has
no legacy fallback after selecting its writer; see
[C06](../planning/MUSU-38-shared-runtime.md) and
[first C07 DELETE evidence](../planning/MUSU-39-google-delete.md).

The historical 0080 warning concerns pre-shared-task writers; it does not settle
0.2.3 → 0.2.2 compatibility. Assess the exact prior image against the actual
journal, Graph read behavior, persisted v1 operations, task/event state and
provider effects before any image-only rollback. If recovery requires a
restore, use a clean database, the verified preupgrade dump and exact prior
API/web digests, configuration, encryption keys and consistent media. Verify
journal, login and authenticated reads before reopening traffic. A database
restore does not undo provider effects: reconcile delivered or uncertain
operations from the incident record and never blindly repeat CREATEs. Do not
rewrite migration history, delete receipts or run pre-0080 task writers against
the shared-task database.
