## Operator sequence when publication and deployment are authorized

1. Record the accepted final source SHA, passing Quality run, previous running
   API/web digests and revisions, actual migration journal, existing gates and
   content-free task/calendar/provider-mapping counts. Also record unresolved
   event/task outboxes and Outlook move journals. Keep credentials, encryption
   keys and private content out of the release record; preserve the required
   keys/configuration separately.
2. Hold public API access in maintenance and stop the API and workers. Create a
   custom PostgreSQL dump with `./ops/backup-postgres.sh`; pass the absolute
   Dokploy Compose path as `MUSUBI_COMPOSE_FILE` when applicable. Preserve local
   media when `S3_BUCKET` is unset and follow the existing remote-media backup
   policy. Restore the dump in isolated PostgreSQL with
   `./ops/verify-postgres-backup.sh /absolute/path/to/backup.dump`. The helper
   proves restore completion and nonempty public tables; additionally compare
   the restored journal and counts with the source record.
3. After the publication hold is cleared, record both published immutable index
   digests, architecture coverage and OCI revision labels from the existing
   workflow. Use the matching artifacts from that accepted revision. Keep the
   prior digests as recovery references; `latest` is not a recovery reference.
4. Start **one API replica**, with the previous API stopped. The singleton lock
   precedes migration and listening; do not use an overlapping start-first
   update. Verify its actual digest/revision, migrator completion, unchanged
   expected journal, `/api/v1/server/ok`, advertised 0.2.3/minimum 0.2.0 and
   authenticated calendar/task reads. Compare the preserved counts and task
   home/memberships, including tombstones, before public traffic.
5. Start the matching web artifact. With an approved test account, verify login,
   calendar/event reads, task create/edit/complete/read, failure/draft behavior
   and delivery status. Check independent provider readback for supported test
   operations; a local receipt alone is insufficient. Record unresolved native
   distribution and physical-device checks explicitly, retaining the v0.2.2
   task-write guidance. No new native build is distributed by this procedure.
6. Check the web branding on the live artifact: favicon, Apple icon, app-specific
   OG, both themes, a coloured calendar mark, original loading/offline fallback
   and notification worker icon/scope/click behavior. Reopen public access only
   after maintenance checks pass, then observe sync/discovery failures, task and
   event queues and uncertain operations. The 0.2.2 runbook contains the
   content-free SQL aggregates; compare them before and after the smoke checks.

## Recovery decision

Stop the API and block writes before recovery. Save an incident dump and the
actual journal, queue state and accepted operation evidence. Prefer a compatible
forward fix when accepted writes need to be retained.

This candidate adds no migrations beyond v0.2.2; the historical warning about
0080 concerns the pre-shared-task writer and does **not** by itself establish
that a 0.2.3 → 0.2.2 switch is unsafe or safe. Assess the exact prior image's
compatibility with the actual journal, task/event state and provider effects
before any image-only rollback. If recovery requires a database restore, use a
clean database, the verified preupgrade dump and exact prior API/web digests,
configuration, encryption keys and consistent media. Verify journal, login and
authenticated reads before reopening traffic. A database restore does not undo
provider effects; reconcile delivered or uncertain operations from the incident
record and never blindly repeat CREATEs. Do not rewrite migration history,
delete receipts or run pre-0080 task writers against the shared-task database.
