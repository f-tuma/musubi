# Musubi 0.2.8 release notes

Microsoft task reads now reject incomplete successful responses before returning
changes, a checkpoint or authority to sweep missing tasks. Delta pages require a
value array and exactly one valid next or terminal delta link. Snapshot reads
finish only after every page is valid. Partial responses, malformed items,
conflicting links and cyclic or over-budget pagination fail the whole read.
Valid empty terminals, sparse updates, replayed IDs and existing source, pending
and late-write protections remain supported.

For a narrowly recognized bootstrap failure, task sync can use the existing
complete snapshot path: HTTP 400, exact Graph `BadRequest`, and the complete
known missing-skip-token message during the actual initial request or its 410
renewal. Saved-cursor and next-page failures, other messages and other status
codes retain their error behavior. The snapshot returns a reset and null cursor
only after successful complete reading; no stored continuation is rewritten or
cleared before that result. Subsequent syncs can try delta again.

Task HTTP diagnostics add a bounded failure-kind classification. Separate log
events distinguish selecting fallback from completing its snapshot read. Neither
event proves that the engine committed changes. No provider message, response
body, task-list identity, request URL or token is logged by these diagnostics.

This is a scoped recovery path, not a claim to have identified a Microsoft
service bug. The owner-authorized Graph Explorer check reproduced the separately
supported delta-unavailable case, not the production missing-skip-token case.
Mailbox-unavailable 404 remains a separate investigation.

## Upgrade and acceptance

There is **no new database migration relative to 0.2.7**; the source journal
still ends at `0085_graph_read_coverage`. Client and peer minimums remain 0.2.0.
Provider gates, OAuth permissions, encoder/recovery configuration, Vardum
artwork, marketing and native store distribution are unchanged. This release
also includes the separately reviewed CI cache and timing-weight improvements.

Use the [existing deployment and recovery procedure](0.2.3-deployment.md).
Publish with `version=0.2.8` and the full reviewed `expected_source_sha`. A new
tag can automatically deploy API and web. Keep source approval, current-head CI,
immutable image publication and actual running observations separate.

After rollout, verify the bounded fallback reason, completed snapshot reading
and successful application independently. Other task HTTP failures must still
expose their bounded phase and failure kind, while calendar reads continue.
Do not treat disappearance of an old message substring as recovery or claim all
accounts recovered from aggregate counters alone.
