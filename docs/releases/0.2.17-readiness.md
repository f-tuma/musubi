## Verified against `v0.2.16`

Checked with `git diff v0.2.16..origin/main` at main `7d146cb9`:

- No changes under `packages/db` or `apps/client/drizzle`. The migration
  journal still has 88 entries, `0000` through `0087_project_news`.
- No changes to `.github/`, any Dockerfile, or the environment variables read
  by production code. The only new `process.env` lines set test defaults.
- No changes to `packages/types`, so `MIN_CLIENT_VERSION` and
  `MIN_PEER_VERSION` stay `0.2.0`. The wire contract and task mutation
  protocol are unchanged.
- No new persisted state. The foreground reserve is in-process scheduler
  configuration (`foregroundReserve: 1` at capacity 4). The 503 event-write
  path commits no event or outbox row. A deferred ICS import keeps the
  calendar it created, which the old error path already did. Federation
  address pinning is in-memory transport.

This branch changes only the root `package.json` version and
`packages/types/src/version.ts` `PRODUCT_VERSION` (0.2.16 → 0.2.17). Workspace
packages and `apps/client/app.config.ts` inherit the root version. No mobile
EAS build, submission or distribution is in scope. CI Android validation still
builds APK/AAB artifacts that report 0.2.17, but nothing distributes them.

## Known limits

- A held background pull of the same account still serializes that account's
  own preflight and delivery.
- Durable recovery work, capability checks and other interactive requests
  share the single reserved foreground slot.
- Client timeout budgets are unchanged. Neither this release nor its tests
  promise a complete performance fix.
- A deferred whole-calendar ICS import is not idempotent. Its 503 receipt
  reports `localCommitted: true` and `imported: 0`, and clients must not
  repeat it automatically.

## Rollback

0.2.17 adds no migration and no new storage semantics relative to `v0.2.16`.
So an image-only rollback to the previously verified 0.2.16 immutable images
is schema-compatible, with no database restore. The 0.2.16 acceptance record
lists those indexes (API `sha256:4fbefa2b…`, web `sha256:2ca520be…`). Confirm
them against the runtime observed before deployment.

- Keep the runbook's stop-first, single-API discipline: stop the 0.2.17 API
  before starting the old one.
- Do not restore the database automatically. A restore would discard real
  writes made after the backup, and it cannot undo changes already delivered
  to providers (`docs/releasing.md`, Releases & Upgrades).
- A rollback brings back the incident behavior: other accounts' pulls can
  again hold every slot, and preflight waits return 403. Prefer a reviewed
  forward fix.
- Do not clear cursors or queues, weaken guards, rewrite migration history or
  replay uncertain writes.
