# 0.2.3 API/web publication workflow audit

Source audit, **14 October 2026**. The audit starts from
`ce7b751ff0b618541d773a342e114006b3ccf893` ([PR #352](https://github.com/f-tuma/musubi/pull/352));
[main Quality run 38444284238](https://github.com/f-tuma/musubi/actions/runs/38444284238)
passed all 21 jobs at that SHA. This document records publication-control
changes and operator-reported behavior. It records no publication, deployment,
production backup or live provider acceptance.

## Confirmed release path

The operator confirmed that a new GitHub tag automatically deploys **both the
Musubi API and `Musubi/apps/web`**. Updating Docker's mutable `latest` alone does
not deploy. The marketing repository `musubi-web` is outside this release.

The repository's four workflow definitions are `quality.yml`,
`docker-publish.yml`, `ios-widgets.yml` and `vardum-assets.yml`. None defines a
production Dokploy deployment job. `Publish Docker images` is a manually
started release workflow: reusable Quality → prepare → four native image
builds → two manifest publications → deployment tag → GitHub release body.
The external tag consumer's installed delivery/configuration and actual rollout
history are operator evidence, not proved by these GitHub job definitions.

The existing pinned checkout, Buildx and Docker login/build/artifact actions
are retained. The release action is replaced by a strict create-only command.
DockerHub secret names and the release job's
`contents: write` are configured in YAML; successful authentication and actual
artifact publication must be observed in the authorized release run. No new PAT,
GitHub environment, deployment endpoint call or artwork upload is introduced.

## Findings at the audited baseline and corrections

| Baseline finding | Correction |
| --- | --- |
| [Line 39](https://github.com/f-tuma/musubi/blob/ce7b751ff0b618541d773a342e114006b3ccf893/.github/workflows/docker-publish.yml#L39) checked only `GITHUB_REF_NAME=main`; a tag named main was not distinguished, and no approved SHA input bound dispatch to the accepted candidate | Require `GITHUB_REF=refs/heads/main`, a full lowercase 40-character `expected_source_sha`, matching captured `github.sha` and checkout HEAD; explicitly pin prepare/build/release checkouts to that captured SHA |
| [Line 49](https://github.com/f-tuma/musubi/blob/ce7b751ff0b618541d773a342e114006b3ccf893/.github/workflows/docker-publish.yml#L49) treated every failed tag API request as absence and checked only before long builds | First establish authenticated Git-content access; require valid JSON Not Found/404 responses for tag/release lookups, reject visible matching drafts via a paginated release list, reject unknown results, and repeat with the release job's write-capable token immediately before tag creation |
| [Line 179](https://github.com/f-tuma/musubi/blob/ce7b751ff0b618541d773a342e114006b3ccf893/.github/workflows/docker-publish.yml#L179) delegated tag creation to a create-or-update release action without proving this run owned a new tag at the approved SHA | Push the exact approved commit to the full tag ref using non-force Git; require porcelain `[new tag]` success and exact remote verification, then use a strict create-only release POST after rechecking the owned source |

`target_commitish` does not validate an already existing tag: GitHub ignores it
when that tag exists. Separate fresh creation/verification therefore precedes
release publication. [GitHub release API documentation](https://docs.github.com/en/rest/releases/releases#create-a-release)

The audited release action can update a release it finds, including a release
that appears after an earlier absence check. That behavior is inappropriate for
this no-adoption release boundary. It is replaced with a single POST to create
a release, using the source notes body and `generate_release_notes=true`.
HTTP 201 is required; conflicts, failures and uncertain responses are HOLD.
There is no PATCH/PUT/DELETE path or automatic creation retry.
[Audited action source](https://github.com/softprops/action-gh-release/blob/3bb12739c298aeb8a4eeaf626c5b8d85266b0e65/src/github.ts#L535)

Release-list checks reject matching drafts visible to the token; a published
release lookup alone does not establish absence of all drafts. The final tag
check uses the release job's `contents: write` token. Strict creation preserves
the no-edit boundary even for a hidden or raced release: it cannot adopt or
modify that release. The release command additionally requires
`OWNED_TAG_SOURCE_SHA` from the successful tag step to equal the captured source
and verifies the exact remote tag again. A rerun without fresh tag ownership
cannot pass this prerequisite.

A non-force push to `refs/tags/*` cannot replace an existing tag. An already
up-to-date tag also does not prove ownership of its creation, so it fails the
fresh-tag requirement. The full SHA/refspec and exact remote verification avoid
ambiguous abbreviated refs. [Git push documentation](https://git-scm.com/docs/git-push)

The guard uses the workflow token and checkout's existing authentication. A
`GITHUB_TOKEN`-generated event normally does not start another GitHub Actions
workflow, apart from the documented dispatch exceptions. That rule concerns
Actions recursion; it does not establish failure of the operator-confirmed
external tag deployment consumer. No substitute PAT or manual deployment call
is added. [GitHub workflow-trigger documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

## Publication and failure boundary

Before dispatch, record the final reviewed, green release-control source SHA in
MUSU-15 and the operator handoff. Select `main`, `version=0.2.3` and the exact
full SHA as `expected_source_sha`. A moving main cannot silently substitute a
new candidate; the guard compares the captured run source rather than requiring
main to remain stationary while builds run.

Both architecture sets must build before either version/`latest` manifest is
published, and both manifest jobs must pass before the final guard and tag push.
The two registry publications are not atomic: failure can leave one image tag
published and the other absent. Concurrency serializes this workflow's runs;
it cannot lock other publishers or Dokploy. Existing visible tag/release conflicts or
unknown API responses halt before a new tag is intentionally pushed. A hidden
or concurrently created release can still conflict after the tag is pushed;
strict POST prevents an edit, but it cannot undo a deployment signal.

Tag creation is the deployment boundary. A lost push response or failed remote
verification can leave a real tag and a running deployment; the guard returns
HOLD. A following GitHub release-body failure can likewise occur after deployment
starts. Inspect the exact remote tag, release, run and actual deployment state
with the operator. **Do not delete, recreate or force the tag, adopt another
publisher's tag, or automatically rerun the whole publication workflow.**
Reconcile the observed state before deciding how to resume any remaining step.

This YAML has no protected production environment or operator-approval gate.
The workflow publishes artifacts and a tag; it does not enforce API→web order,
stop old API/workers, prove singleton ownership, compare the real migration
journal, make a production backup or restore it. Those operational requirements
remain in the [deployment/recovery guide](0.2.3-deployment.md) and
[readiness record](0.2.3-readiness.md). Operator-confirmed tag/`latest` behavior
closes the trigger question but does not close these other fields.
