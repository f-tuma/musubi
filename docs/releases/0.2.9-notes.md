# Musubi 0.2.9 release notes

A narrowly recognized unavailable Outlook mailbox no longer prevents reading
independently granted Microsoft To Do lists. Only an initial calendar-discovery
HTTP 404 with the exact Graph mailbox eligibility code selects this path.
Existing event mirrors, source identity, access state, cursors, coverage and
pending writes are retained, and event reads are skipped before read admission.
Tasks continue through their usual reconciliation and linked-calendar
invalidation path. The account still reports the mailbox failure after Tasks
apply; this release does not provision a mailbox or hide its error from alerts.

Calendar and task-list discovery now validate every collection page before
returning an authoritative inventory. Missing or malformed collections, invalid
items, duplicate IDs, partial responses, unexpected continuation targets and
cyclic or excessive pagination fail the whole inventory. Event IDs that collide
with the reserved task-list namespace are rejected before reconciliation.
Opaque valid IDs and continuation bytes are preserved. A valid complete empty
inventory retains its ordinary removal semantics.

This release also includes the previously reviewed bounded calendar-discovery
HTTP diagnostics. Unknown or bare 404s, later-page failures and authentication
errors retain their failure behavior. It does not change CalDAV discovery,
resolve the observed iCloud principal-alias rejection, or establish recovery for
any live account. Those require separate provider evidence.

## Upgrade and acceptance

There is **no new database migration relative to 0.2.8**; the source journal
still ends at `0085_graph_read_coverage` (86 entries). Client and peer minimums
remain 0.2.0. OAuth permissions, provider gates, encoder/recovery configuration,
web artwork and native store distribution are unchanged.

Use the [existing deployment and recovery procedure](0.2.3-deployment.md) with
`version=0.2.9` and the final reviewed full `expected_source_sha`. The operator's
existing instruction to proceed with automatic backups is an authorization,
not evidence of a verified restore, running database journal, maintenance or
consumer replacement. Record those operational limits separately. A new tag
can deploy both API and web; source review, green checks, immutable publication
and actual running revisions are separate evidence.

After rollout, verify this account's bounded calendar-discovery status/code and
independent task application separately. Confirm that retained event state is
preserved, Tasks reach both source and linked calendars, and the unavailable
mailbox still reports failure. A later complete calendar inventory must resume
normal reads. Zero matching logs or aggregate account counters alone do not
prove recovery. The iCloud incident remains open pending a read-only identity
check and a separately reviewed fix.
