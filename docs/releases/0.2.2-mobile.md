# Musubi 0.2.2 mobile preparation

Final signed artifacts are Android **0.2.2 / versionCode 66** and iOS
**0.2.2 / build 19**. On 2026-10-05 the operator reported Android submitted to
Play review and opening the iOS app on an iPad. iOS upload is complete; the
installed iPad build number and full physical acceptance are not recorded.
See [release status](https://musubi.pro/docs/operations/releases/) for the
distribution snapshot. Build and submission commands below are the procedure,
not a request to create replacement artifacts.

A new Android/iOS store build is required to write tasks against the 0.2.2 API.
This project has no `expo-updates` or OTA channel. An installed 0.2.0/0.2.1 build
keeps its original task request code until the user installs an update.

## Compatibility during rollout

| Installed client | Connected API | Task reads | Task writes |
| --- | --- | --- | --- |
| 0.2.0/0.2.1 | 0.2.0/0.2.1 | Existing behavior | Existing behavior |
| 0.2.0/0.2.1 | 0.2.2 | Available through retained `/api/v1/tasks` DTO routes | Legacy write routes return 426 before a provider preflight or database write |
| 0.2.2 | 0.2.0/0.2.1 | Retained read routes remain usable | New `/api/v1/task-mutations` routes are absent: 404, no fallback or local acceptance |
| 0.2.2 | 0.2.2 | Available | Revision/privacy checks and explicit committed receipts; shared links and independent copies |

Creating, editing, completing, changing priority and deleting tasks all use the
new write protocol. This applies to ordinary tasks as well as shared tasks.
The 426 message asks the user to update Musubi and says the changes were not
saved. The released editor keeps the draft open; status/priority actions show an
error rather than reporting successful acceptance. Neither protocol mismatch
may create a duplicate task on retry. Until the store update is available, use
the current web client for task changes.

`MIN_CLIENT_VERSION` and `MIN_PEER_VERSION` stay at **0.2.0**. Older clients can
still read tasks and use compatible event/calendar features. Raising the global
minimum would lock those users out of the whole app and would not make their
legacy task DTO requests safe. The route selects the task protocol; a claimed
version header never substitutes for revisions, privacy checks or authority.

Installing 0.2.2 requires signing in again. Native credential storage now uses a
collision-free full-origin namespace (including HTTP versus HTTPS). Ambiguous
legacy credential keys are deliberately not imported into an arbitrary server.
The first startup prepares the local schema and clears legacy account cache,
widgets and scheduled reminders before opening authentication. A failed cleanup
cannot mark that transition complete. New sessions retain normal persistence
across process restarts. Cache ownership is checked against the current server
and user before navigation; expired sessions and account changes clear previous
content, while the same account retains its offline cache.

The existing global update screen therefore does not force a 0.2.0/0.2.1 user to
install 0.2.2. The task write error is the update guidance for this release.
See the [shared-task contract](../sync/shared-tasks.md#clientapi-compatibility-and-rollout).

## Build metadata and configuration

- Root `package.json` and `PRODUCT_VERSION` in `packages/types/src/version.ts`
  declare **0.2.2**. `apps/client/app.config.ts` reads the root version directly.
- `eas.json` uses `appVersionSource: "remote"`; production uses
  `autoIncrement: true`. EAS increments Android `versionCode` and iOS
  `buildNumber` from the existing remote counters. Do not reset those counters
  or hardcode them to the product version.
- The production profile selects the EAS **production** environment. iOS is
  currently a TestFlight beta; the profile supplies the existing public
  `EXPO_PUBLIC_IOS_TESTFLIGHT_URL=https://testflight.apple.com/join/EqzdPVfC`.
  The update screen names and opens **TestFlight**. A future real
  `EXPO_PUBLIC_IOS_APP_STORE_URL` from the EAS environment takes precedence.
- Production **iOS** requires a valid App Store or TestFlight update destination.
  Android does not require an iOS URL. Supplied App Store URLs must have a
  nonzero app ID; TestFlight URLs must name the HTTPS Apple join endpoint.
  Unconfigured development/preview builds retain **Open download page**.
- The code changes add no native dependency or permission. Shared task titles,
  notes and calendar memberships are user content sent to the selected Musubi
  server and user-selected providers. Review the existing Play Data Safety
  declaration for that content; no new advertising/analytics collection is added.

A passing API/web release metadata check does not establish iOS distribution
readiness. EAS signing access, actual platform build numbers, TestFlight/store
submission and on-device smoke tests remain operator checks. A public App Store
listing is not required while iOS is distributed through the configured beta.

## Preparation and operator commands

Run the local checks from the release checkout:

```sh
pnpm release:verify 0.2.2
node --test scripts/verify-release.test.mjs
pnpm --filter @musubi/client exec vitest run
pnpm --filter @musubi/client exec tsc --noEmit
```

To check platform-specific dynamic Expo configuration without creating a build:

```sh
cd apps/client
EAS_BUILD_PROFILE=production EAS_BUILD_PLATFORM=android pnpm exec expo config --type public
# Check the real production profile, including its beta URL and environment.
eas config --profile production --platform ios --non-interactive
```

Use the already authenticated EAS CLI at the version required by `eas.json`.
The following are release operator actions: they create remote build jobs and
must be run only when ready to build. They are not part of local verification.

```sh
cd apps/client
eas build --profile production --platform android
eas build --profile production --platform ios
```

Record the release commit, EAS build IDs, product version and platform build
numbers for both artifacts. Test the production artifacts on devices before
selecting those exact artifacts for store submission. Do not use an ambiguous
“latest” artifact selection after unrelated builds.

## Release order and smoke checks

Prepare native artifacts against a 0.2.2 test API first. The normal production
order remains **API → web → native distribution**: a new client cannot write to
an older API. Prefer store readiness before the API switch to keep the period
without mobile task writes short. If the API/web ship earlier, record explicitly
that old mobile task writes are temporarily unavailable and direct users to web.

Verify on the actual Android/iOS artifacts:

1. Sign in and select the intended production/test server; confirm 0.2.2 in app
   settings and the recorded platform build number.
2. Create, edit, complete/reopen and delete an ordinary task. A failed save keeps
   the draft open; a received committed receipt updates the UI once.
3. Link a task to an allowed Google/CalDAV/local destination and verify home
   permissions. A read-only member cannot edit or complete the canonical task.
4. Make an independent copy, lose the committed response and retry the same
   attempt. Recover one copy, including after the source task changes.
5. Microsoft To Do is available for independent copies when ordinary creation is
   supported, and excluded from new live links. An existing unsupported link
   shows its remediation state and does not gain a conditional-write bypass.
6. Refresh delivery status, notifications and realtime task updates. Reconnect a
   provider when requested, then verify a live task sync rather than assuming a
   successful API health check proves provider delivery.
7. Retain one released 0.2.0/0.2.1 artifact for the mixed rollout check: reads and
   compatible event features work, task saves get the update message without a
   committed write, and the current web client can save tasks.

A native build/export or mocked unit run is not a substitute for these device
and live provider checks. Record any checks intentionally deferred before the
production switch in the [0.2.2 release runbook](0.2.2-deployment.md).

Expo references: [app version management](https://docs.expo.dev/build-reference/app-versions/)
and [EAS environment variables](https://docs.expo.dev/eas/environment-variables/).

## Android Play recommendations after build 66

On 2026-10-06 Play reported a portrait restriction on
`dev.frgtn.musubi.MainActivity`. The next Android build uses Expo
`orientation: "default"`; prebuild and the packaged release manifest now contain
`screenOrientation="unspecified"`. Neither the activity nor the application
disables resizing or sets an aspect-ratio restriction. The welcome screen can
scroll in short windows so its content and account/server buttons do not overlap.
The existing iOS orientations are retained explicitly in `ios.infoPlist`.
Android authentication forms use the activity's `adjustResize` behavior rather
than a keyboard-avoidance height captured before rotation. Short month cells
show an inline hidden-item count instead of drawing chips or all-day bars into
the next week. Hidden all-day items are counted independently of spare timed
rows. Task detail text reads the current theme color after a light/dark switch.

The inspected APK targets API 36. Android 16 overrides these restrictions on
large screens for apps targeting API 36; removing them also permits rotation on
older Android versions. See the [Android adaptive-app guide](https://developer.android.com/develop/adaptive-apps/guides/app-orientation-aspect-ratio-resizability)
and [Expo orientation configuration](https://docs.expo.dev/versions/latest/config/app/#orientation).

Play also reported deprecated status/navigation-bar color and cutout APIs in
React Native and Google Material classes. The orientation change alone does
**not** clear that recommendation. The 2026-10-07 native migration below removes
the reported calls from the shipped RN 0.86.3 / Material 1.13.0 paths without a
dependency upgrade. Its effect on Play's recommendation remains pending analysis
of a newly uploaded, signed store AAB.

Build 66 already uploaded to Play retains its original manifest and code. These
changes require a new Android store build with a higher versionCode; they cannot
be applied through OTA. Physical tablet/foldable and multi-window acceptance,
along with the Play analysis of that new artifact, remain release checks.

### Native system bar migration on 2026-10-07

Musubi permanently uses edge-to-edge windows. The Expo config plugin
`apps/client/plugins/withModernSystemBars.js` supplies transparent activity,
bottom-sheet and side-sheet window themes and registers a narrowly scoped
[AGP ASM transformation](https://developer.android.com/build/releases/gradle-plugin-api-updates).
The transformation replaces obsolete window-color management in
`WindowUtilKt`, `StatusBarModule` (including nested classes), Material
`EdgeToEdgeUtils`, `BottomSheetDialog` and `SheetDialog`. Insets, system-bar
visibility, contrast enforcement and icon appearance remain the libraries'
existing code. Colors come from the transparent window themes and content
backgrounds; legacy color getters return transparent, and setters are omitted.
This is an application-specific compatibility patch, not an upstream SDK fix.

Cutout requests use `LAYOUT_IN_DISPLAY_CUTOUT_MODE_ALWAYS` on API 30 and newer.
On API 24–29 the helper leaves the existing platform-safe attributes unchanged;
it does not substitute an unsupported newer constant. A library-version guard
rejects a different RN/Material binary contract before applying the patch. Every
release build also audits the actual pinned AAR classes with the same visitor.
Reassess and remove the specialization when a compatible upstream implementation
makes it unnecessary.

Local verification passed:

- Release APK and AAB builds for all four production ABIs; 15 AAR classes and
  15 migrated legacy calls. The DEX scanner covered five DEX files and 20
  selected classes, including generated nested classes, in each artifact.
  Neither artifact contains the old color calls or direct cutout writes in
  those paths. Eleven color calls in unrelated compatibility classes remain
  and are reported separately; this is not an assertion that every deprecated
  API in the whole artifact has disappeared.
- 513 client tests, typecheck and zero-warning lint for the config/plugin;
  five Python/JVM checks for scanner failures and cutout behavior on API
  24/28/29/30/35/36. Repeat prebuild updates the generated integration without
  duplicate blocks and rejects incomplete generated blocks.
- Android 11 / API 30 and Android 16 / API 36 phone emulators: actual Musubi
  welcome/login and keyboard, light/dark status icons, native Material bottom
  and side sheets, dismissal, and RN status-bar hide/show with restored insets.
  API 36 additionally exercised the native dialogs at tablet landscape size.
  No Android runtime exception occurred in these targeted checks.

Material and explicit RN window operations were exercised using a temporary
activity in ignored generated Android source. The harness and its temporary
compile-only access to the already-shipped Material library were removed, then
the production configuration was regenerated and rebuilt. No QA activity,
manifest overlay or extra dependency is committed. These checks cover this
native compatibility change, not authenticated provider writes or physical
foldable/multi-window acceptance.

The `Android system bars` CI job builds arm64 and x86_64 APK/AAB artifacts and
runs `scripts/verify-android-system-bars.py` against their shipped DEX. Production
store builds retain all configured ABIs. The AAR report is saved as CI evidence;
a native dependency update cannot silently retain this unreviewed patch.

A new signed Android build with a higher versionCode is still required. Local
Gradle artifacts use local signing and are not for store submission. Record the
exact EAS build/commit, verify the signed AAB with the DEX scanner, upload that
artifact, and check Play's new analysis before closing the recommendation.
The migration changes Android native code only; it does not require an iOS
store update.
